# 통사구조 중심의 업무 표현과 SAP 사례 대조

작성일: 2026-10-22. 구현 대조 기준: `c10ed6f8`.

## 1. 목표를 다시 정렬한다

**업무의 대상·행동·조건을 통사구조로 표현하고 조합해, 사람과 Agent가
같은 의미로 업무를 읽고 필요한 절차를 구성하도록 한다.**

수입·유통은 이 업무 언어를 검증할 구체적인 도메인이다. SAP는 실제
업무 의미·표준 기능·연동 경계를 대조하는 기준이자 향후 연결 대상이다.
CAP는 구현 수단이다. SAP의 객체 이름을 닮게 만드는 것이나 ontology
기술을 더 많이 도입하는 것으로 목표 달성을 판단하지 않는다.

사용자는 SAP 사례 검증과 통사구조 중심의 정렬을 요청했고, 시험
tenant가 없으므로 공식 문서·API 명세와 로컬 사례부터 대조하도록 했다.
이번 결과는 문서와 소스의 의미 대조다. SAP API 호출·DB 실행·실모델
평가 결과가 아니며, mock 응답을 실제 SAP 응답으로 제시하지 않는다.

기존 D01–D26과 S0–S6의 범위·인수 조건은 유지한다. 아래 대표 사례는
설계 설명과 검증을 연결하는 공통 사례이며 전체 인수를 대체하지 않는다.

## 2. 같은 단어를 조합하되 문장의 역할을 구별한다

통사구조는 자연어 품사를 데이터 테이블로 일대일 변환하는 규칙이
아니다. 대상의 유형, 행동에 필요한 역할, 속성·조건의 결합을 정하는
업무 표현의 틀이다. 동사도 관계·활동·목표 업무를 구분한다.

다음은 설명용 표현이며 새로운 parser나 실행 API 문법이 아니다.

| 표현 | 구조와 의미 | 실행에 넘기기 전 확인할 것 |
|---|---|---|
| “창고 W에 있는 품목 P의 물량 Q” | 대상 Q + 품목/장소 관계 | Q의 식별자, 시점, 조회 범위 |
| “Q 100 BOX를 금요일까지 고객 C에게 인도하라” | 인도 업무 + 대상/수량/받는 이/기한/끝점 | 단위·고객·장소·GoalVersion·실행 권한 |
| “Q 중 80 BOX를 C에게 인도했다” | 발생한 활동에 대한 보고 | 사건·범위·발생 시각·근거, 동일 사건 여부 |
| “C가 Q 중 20 BOX의 인수를 거부했다” | 행위자 C의 판단/행동에 대한 보고 | 명시적 거부 근거, 이유, 대상 범위; 차이 수량만으로 생성 금지 |
| “이번 주 인도한 P의 물량과 관련 업무를 보여줘” | 대상·활동·시간 조건을 조합한 조회 | 조회를 새 인도나 반품 명령으로 바꾸지 않음 |
| “그 거부의 원인을 확인할 절차를 제안해줘” | 앞선 사실을 참조하는 계획 요청 | 기존 관련 업무·담당·의무, 필요한 입력과 지원 capability |

품목 P에서 인도 업무 W를 열든, W에서 P의 물량 Q를 열든 같은
ID·시점·수량·근거·책임을
읽어야 한다. 새 조합을 해석해도 사실을 만드는 권한이 늘어나지는 않는다.

## 3. SAP에서 확인한 경계

새 비교의 기준은 **SAP S/4HANA Cloud Public Edition 2608**의 도움말이다.
아래 V01–V05는 [출처 기록](research/sap-relevance-sources.md)의
S22–S26과 연결된다. 이전 보고서의 on-premise·EAC 자료를 이 API
계약에 섞지 않는다. 실제 연결 전에는 대상 tenant의 지원 버전과
communication arrangement를 따로 확인해야 한다.

| 근거 | 확인한 공개 명세 | 우리 모델로 옮길 때의 판단 |
|---|---|---|
| V01 / S22 | `API_OUTBOUND_DELIVERY_SRV;v=2`의 출고 문서 GET과 item 확장 조회 | 출고 문서와 item을 조회하는 경로는 확인됐다. 우리 Work·QuantitySegment ID로 자동 대응하지는 않는다. |
| V02 / S23 | `A_OutbDeliveryItem`의 문서/item, Material, Batch, 수량/단위, POD 상태 | `ActualDeliveryQuantity`는 고객이 인수를 수락한 수량의 증거로 바로 쓰지 않는다. 문서 수량과 고객 확인은 별개다. |
| V03 / S24 | `ProofOfDeliveryQtyInSlsUnit`, 차이 수량, 사유를 다루는 POD node | 보고된 수량과 차이를 표현할 수 있다. 차이의 사유·증거 없이 “고객 거부”로 분류할 수는 없다. |
| V04 / S25 | Proof of Delivery – Update (B2B)는 SOAP로 분류된다. | 이 쓰기 명세에서 POD 수량을 발견했다고 OData GET으로 같은 정보를 읽을 수 있다고 가정하지 않는다. POD 읽기/원천 확보는 미해결이다. |
| V05 / S26 | Returns Inspection의 OData v4 조회·갱신 등 operations | 반품 후 검사 경로가 존재한다. 출고 시점의 거부와 사후 반품 검사를 같은 사건으로 만들지 않는다. |

확인한 조회 형식은 다음과 같다. `<host>`와 ID는 설명용 placeholder이며
실행하지 않았다. 첫 요청만으로 거부·손실 보고서가 완성되지는 않는다.

```http
GET <host>/sap/opu/odata/sap/API_OUTBOUND_DELIVERY_SRV;v=2/A_OutbDeliveryHeader(DeliveryDocument='<delivery-id>')?$expand=to_DeliveryDocumentItem
GET <host>/sap/opu/odata4/sap/api_returnsinspection_2/srvd_a2x/sap/returnsinspection/0001/ReturnsInspection?$top=50
```

### 필드 대응은 이름보다 의미를 먼저 검사한다

| 필요한 의미 | 확인한 SAP 필드 또는 추가 원천 | 대응 조건 |
|---|---|---|
| 외부 문서/item 식별 | DeliveryDocument, DeliveryDocumentItem | source system·tenant와 함께 식별하고 내부 UUID에 명시적으로 연결한다. |
| 품목·LOT | Material, Batch | 품목/제조자/LOT의 식별 범위를 확인한다. 같은 문자열만으로 병합하지 않는다. |
| 문서 수량·단위 | ActualDeliveryQuantity, DeliveryQuantityUnit; ActualDeliveredQtyInBaseUnit, BaseUnit | 둘은 같은 물량의 단위별 표현일 수 있다. 합산하지 않고 승인된 환산 의미를 확인한다. |
| 고객 확인 수량 | POD 보고와 증거 | V03은 입력 명세다. 실제 읽기 원천과 확인 상태를 확보한 뒤 사실 후보로 사용한다. |
| 고객 인수 거부 | 명시적인 거부 사건·사유·대상 물량의 원천 필요 | POD 차이·목표 미기여·반품 수량을 대체값으로 쓰지 않는다. |
| 단가·손실 | 가격 기준·단위·통화·시점·손실 정책과 관련 거래 증거 필요 | 이 조사에서 가격 API를 선정하거나 손실 산식을 확정하지 않았다. |

## 4. 로컬 구현과 대조한 결과

다음 판정은 소스 읽기 결과다. 실제 실행 통과를 뜻하지 않는다.

- [공개 slot](../contracts/capability-slots.json)의 `recordDelivery`와
  [DeliveryCommands](../backend/src/main/java/com/mulino/application/trade/sales/DeliveryCommands.java)는
  관측 접수와 canonical 사건 확인을 구분한다. `physicalQuantity`와
  `contributedQuantity`도 구분한다. 이는 활동 보고와 목표 충족을
  분리하는 철학에 맞는다.
- 같은 handler에서 목표 기여량은 제한·목적지·고객·기한의 영향을
  받는다. 따라서 `physicalQuantity - contributedQuantity`를 고객의
  거부 수량으로 정의하면 안 된다. 늦게 도착했지만 고객이 인수한
  물량도 있을 수 있다.
- 확인한 `recordDelivery` slot에는 고객 거부 수량·사유가 없다.
  이 surface만으로 거부 지표가 완성됐다고 볼 수 없다. 일반 사건·증거
  모델에 연결할 정의와 읽기 경로를 먼저 검토해야 한다. 새로운 명령이
  필요한지는 아직 결정하지 않았다.
- [ReturnCommands](../backend/src/main/java/com/mulino/application/trade/returns/ReturnCommands.java)는
  `authorizeReturn`, `receiveReturn`, `decideReturnDisposition`을 나눈다.
  원 인도 범위를 참조하는 반품과 그 후의 처분을 구별할 자리가 있다.
- [ResponsibilityCommands](../backend/src/main/java/com/mulino/application/responsibility/ResponsibilityCommands.java)의
  `rejectHandover`는 책임 인계의 거절이다. 단어가 비슷하다는 이유로
  고객의 물품 인수 거부를 기록하는 데 쓰면 안 된다.

## 5. 대표 사례와 반례 대조

아래 숫자와 상황은 **작성한 가상 사례**다. SAP 응답이나 운영 자료가
아니다. 사례 A에서만 한 품목·동일 단위·한 주의 한 인도 시도·중복 없는
대상 100 BOX를 분모로, 인수 수락80과 명시적 거부20을 완전히 분류했다고
가정한다. 이는 제품 전체의 KPI 정의를 확정하는 것이 아니다.

| 사례 | 입력과 기대 해석 | 대조 결과와 필요한 검증 |
|---|---|---|
| A. 명시적 부분 거부 | 대상100, 고객 수락80, 근거가 있는 거부20 → 이 사례의 수량 구성비80%/20% | 산술 일치. V01–V03만으로 거부20의 원천은 확보되지 않는다. 고객 거부 근거의 추가 연결이 필요하다. |
| B. 수량 차이만 관측 | 출고 문서100, POD 보고80, 차이 이유 미확인 → 수량 차이20, 거부는 미확인 | V03이 차이·사유를 나누는 것과 맞는다. 거부20%로 출력하면 의미 오류다. |
| C. 기한 초과 인수 | 실제 인도100, 고객 인수100, 기한 초과로 목표 기여0 → 지연/미충족과 고객 거부를 구별 | 로컬 handler의 물리량/기여량 분리가 필요함을 설명한다. 고객 거부100으로 계산하면 오류다. |
| D. 사후 반품 | A의 수락80 중 다음 날5가 반품됨 → 과거 수락 사건과 새 반품5를 연결 | 원래 기록을 수락75/거부25로 덮지 않는다. 현재 순보유 등 별도 지표는 그 정의에 따라 계산한다. V05와 ReturnCommands가 비교 근거다. |
| E. 중복·정정 | 같은 원천 사건의 재전송과, 같은 사건에 대한 수량 정정 | 재전송은 새 인도가 아니다. 정정은 원 버전·시점·범위를 남긴다. 기존 멱등성·정정 인수로 검증한다. |
| F. 단위·가격 미정 | 10 BOX와120 EA의 관계 미확인, 손실 가격 기준 미정 | 130으로 합산하거나 임의 가격으로 손실을 만들지 않는다. 단위 관계·가격 의미를 먼저 확인한다. |
| G. 두 진입점 | “P 물량의 이번 주 인도”와 “이번 주 인도 업무의 P 물량” | 같은 대상·업무·시점으로 좁히면 같은 사건·근거·수량이어야 한다. 실제 두 조회 실행은 별도 필요하다. |
| H. 새 절차 조합 | B의 수량 차이 확인 → 근거 요청 → 명시적 거부라면 후속 처리 검토 | 기존 업무·의무를 확인한 뒤 계획을 제안한다. 사유가 불명확한 상태에서 반품을 자동 실행하지 않는다. 실모델 제안 평가는 미실행이다. |

사례 B·C·D에서는 같은 “거부”라는 말로 서로 다른 사실을 합칠 때의
오류를 확인했다.
새로운 문장 조합에서도 이 구별이 유지되는지가 온톨로지의 검증 대상이다.

## 6. 설계 판단과 구현 증거를 연결한다

| 철학의 검증 질문 | 기존 계약과 연결 | 다음에 남길 실행 증거 |
|---|---|---|
| 새 문장도 대상·행동·조건으로 구성할 수 있는가? | 구현 계획 §3 typed intent·정의, §8 FDE | 동의 표현과 처음 보는 조합의 canonical intent, 미지원 의미를 밝힌 응답 |
| 문장의 역할이 보존되는가? | QUERY / RECORD / COMMAND | 조회·과거 보고·실행 요청을 바꿔치기하지 않는 tool trace |
| 어느 진입점에서도 같은 사실인가? | §3.4 공개 조회 | 같은 scope·asOf·knownAt의 두 조회와 증거 ID 대조 |
| 사실이 부족할 때 무엇을 모르는지 아는가? | UNKNOWN / CONFLICT·증거 대조 | 사례 B·F에서 허위 거부·손실을 만들지 않는 결과 |
| 절차를 조합해도 책임과 권한이 유지되는가? | Work·Obligation·현재 승인·capability | 사례 H의 제안과 실행을 분리한 기록, 기존 의무 중복 여부 |

업무 언어의 확장은 두 종류로 평가한다. 지원된 대상·동사·조건의
새 조합은 기존 capability로 해석·구성할 수 있는지 본다. 새로운 업무
효과가 필요한 요구는 코드·계약 확장이 필요한 이유를 설명해야 한다.
두 경우를 모두 무코드 처리해야 한다는 요구는 아니다.

## 7. 결론과 다음 검증 경계

문서 대조로 출고 문서 조회, POD 차이 표현, 반품 검사라는 SAP의
구체적인 경로를 확인했다. 동시에 **출고/POD/인수 거부/목표 미충족/
사후 반품을 한 상태나 한 수량으로 묶을 수 없음**을 확인했다.
로컬 구현은 일부 구별을 담고 있으나 거부 지표의 원천 대응은 열려 있다.

이번 정렬은 이 구별을 유지하며 업무를 표현·조합하는 것을 중심에 둔다.
시각화는 해석한 의미를 사람이 검토하는 출력이고, SAP 연동은 외부의
업무 의미를 같은 언어로 연결할 수 있는지 시험하는 수단이다.

현재 완료: 공식 문서·공개 API 설명의 대조, 소스의 의미 대응 검토,
가상 사례 A–H의 기대 해석 정리. 미실행: SAP tenant 호출, 실제
adapter mapping, backend 사례 재실행, 실모델·사용자 평가, BTP 배포.

다음 구현 검토는 거부 원천과 POD 읽기 경로를 정하고, 기존 capability로
표현 가능한 부분과 새 효과가 필요한 부분을 구분하는 데서 시작한다.
그 뒤 같은 사례로 두 진입점·제안 trace를 실행 검증한다. 실제 SAP
연결은 tenant와 인증·지원 API가 확보된 뒤 별도로 인수한다.
