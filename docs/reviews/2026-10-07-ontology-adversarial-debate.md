# 온톨로지 설계 adversarial debate 검증

검토일: 2026-10-07 (Asia/Seoul)

## 결론

측정·비교·조사를 개념상 구분하면서 측정은 가벼운 기록으로 보존하고,
운송에는 파생 속성을 보여주며 필요한 경우에만 책임 있는 업무를
연결하는 혼합안을 유지한다. 이를 기각할 명시적인 자기모순은 이번
검토에서 확인하지 못했다. 설계의 완전성이나 구현의 정상 동작을
증명한 것은 아니다.

첫 라운드의 10개 주장 중 핵심 보완은 2개로 좁혔다.

1. 물량 통합 후 계보상 출처와 현재 실물 식별 가능성을 구별해야 한다.
2. 종료 후 정정으로 유효한 미이행 의무가 드러나면 책임 연결이 필요하다.

재측정의 재고 반영, 예약 대체, 버전별 실행기, 외부 기록 식별자는
해당 기능 구현 전 확정할 계약으로 남긴다. 측정·비교마다 Work Item,
Run, 새 범용 엔진을 도입해야 한다는 결론은 나오지 않았다.

이 문서는 검증 결과와 수정 제안이다. 사용자가 채택한 설계 결정이나
코드 변경을 뜻하지 않는다. 원 논의의 제안·합의 구분을 유지한다.

## 핵심 보완 1 — 계보와 실물 식별 가능성 (I1)

문서 근거: D03 733–742행, D16 1210–1214행,
D18 1257–1263행.

### 반례

1. 같은 품목·LOT의 A 40상자와 B 60상자를 Q 100상자로 합친다.
2. 장부에는 A→Q 40, B→Q 60이라는 계보가 남는다.
3. 현재 상자나 구획에서 A와 B를 구별할 수 없게 된다.
4. 뒤늦게 A의 운송 증거가 정정돼 A 범위의 품질 확인이 필요해진다.

이때 원천 영향량은 40이지만 현재 영향 후보량은 100이다.
계보 수량만으로 임의의 40상자를 골라 제한하고 나머지 60을
영향 없다고 판단할 수 없다.

### 반론으로 좁힌 결론

문서는 영향 후보와 오염 확정을 이미 구분한다. 따라서 후보100을
오염 확정100, 무조건 전량 보류 또는 폐기로 바꾸는 수정은 과도하다.
모든 낱개에 일련번호를 붙이거나 모든 합침을 금지할 필요도 없다.

### 최소 수정 제안

> 물량 통합 후에도 과거 부분 범위를 현재 실물에서 구별할 수 있는지
> 기록한다. 식별 근거가 없으면 원천 영향량과 현재 영향 후보 범위를
> 구분하고, 임의의 일부를 영향 밖으로 간주하지 않는다. 제한·해제는
> 해당 범위의 증거와 권한 있는 판단에 따른다.

초기 구현에서 출처를 잃는 통합을 지원하지 않는 방법도 가능하다.
이 선택을 하면 별도의 복잡한 추적 불확실성 엔진은 우선 필요하지 않다.

### 수용 사례

- 계보상 A40과 후보 Q100을 동시에 조회할 수 있다.
- 추가 근거 없이 정상60이라는 가용량이 생성되지 않는다.
- 모든 후보가 오염 확정으로 바뀌지는 않는다.
- 실물 식별 근거를 유지한 통합은 그 근거에 따라 부분 판단할 수 있다.

## 구현 전 계약으로 남긴 4개 항목

### I2. 관측 채택과 재고 변경

문서는 관측·diff와 실제 거래 효과를 이미 구별한다. 부족한 것은
수령 확정·수령 정정·실사 조정 중 어떤 명령이 어느 효과를 변경하는가다.

예를 들어 수령98 뒤 출고10이 있으면 현재고는88이다. 수령 정정99는
수령 기여량을 +1 정정해 현재고89로 이어져야 한다. 현재고를99로
덮어쓰거나 재측정과 문서 정정에서 각각 +1을 반영해서는 안 된다.

- 관측값 채택 자체는 재고 쓰기가 아니다.
- 원 수령 거래·적용 revision과 정정 기여량을 검증한다.
- 같은 수치라는 이유로 다른 시점의 독립 측정을 중복 제거하지 않는다.
- 조회·diff 단계에는 비차단이며 실제 재고 반영 전에는 계약을 확정한다.

새 범용 reconciliation 엔진이나 전역 효과 객체가 필수인 것은 아니다.
기존 트랜잭션·잠금·멱등성 서비스에 도메인 명령을 추가하는 방식부터
검토할 수 있다.

### O1. 대체 예약의 효력

가정: 적격 재고90, 주문 K50. A30+보류 A20의 예약에서 A20을
B20으로 대체한 뒤 A20의 보류가 해제된다.

- 대체가 확정되면 유효 예약은 A30+B20=50이다.
- 과거 A20은 이력이며 적격성 회복만으로 예약이 부활하지 않는다.
- 미예약 적격량은 90−50=40이다.
- 대체 후보를 제안한 시점에 원 배분의 효력을 미리 끝내지 않는다.

이것은 기존 “대체”의 효력을 명료하게 하는 계약이다. 새로운 범용
예약 상태 플랫폼을 도입할 근거는 아니다.

### P1. 정의 버전과 실행기의 호환

현재 `RunCompletionPolicy.java:23–36`은 역할별 완료 근거를 검사한다.
`RunLeaseRepository.java:180–202`과 Work Item 기본 DDL은 새 온톨로지의
정의 버전별 판정기를 제공하는 완성된 계약이 아니다.

D21이 이미 요구한 의미 버전 고정·현재 정책 재검증을 실행하려면
지원 정의 버전→처리기 대응과 미지원 버전의 명시적 거부·전환·보류
정책을 정해야 한다. 정적 Java handler와 제한된 지원 버전부터 시작할
수 있다. 일반 규칙 엔진이나 자동 마이그레이션은 필수가 아니다.

### P2. 외부 수신 식별과 revision

현재 `database/ddl/07_case_management.sql:125–138`과
`DispatcherRepository.java:298–345`는 event type과 external ref를
기반으로 대조하며, `DispatcherService.java:313–319`는 같은 키의
다른 payload를 충돌로 거부한다.

운송사 문서473의98→99 정정과 다른 운송사의 문서473을 구분하려면
원천 namespace + 기록 ID + revision을 안정된 수신 식별자로 대응한다.
동일 revision의 다른 내용은 충돌이고 새 revision은 정정 관계다.

D22의 요구를 기존 `external_ref`에 대응하는 작은 adapter부터 검토한다.
기존 API 재사용을 확정한 것도 아니므로 새 event 테이블이나 범용
동기화 플랫폼이 필요하다는 결론은 나오지 않는다.

## 철회·통합한 반례와 유지할 검증 사례

상위 계약이100을 요구하고60만 측정됐으면40은 미확인이다. 문서가 이미
범위와 실제 결과의 대조를 요구하므로 독립 개념 결함으로 집계하지 않는다.
요약 계산의 입력에 기대 범위를 연결하고 부모 책임 아래 누락을 추적한다.
별도 기대치 객체나 측정별 Work Item이 필수인 것은 아니다.

### G2. 전체 업무 인계와 부분 인계

전체 업무 인수라면 요청 당시 잔량40이 수락 시점에50으로 정정돼도
현재 의무를 추적하는 책임은 새 담당자에게 있다. 단순 진척 갱신마다
재수락을 요구하면 인계가 불필요하게 지연된다.

명시적 부분 인계만 지원할 경우 나머지 의무의 책임을 유지해야 한다.
목표·인계 범위의 변경과 진척 사실의 갱신을 구별한다. 반례가 문서에
없는 부분 인계를 전제했으므로 전체 인계 기본안의 결함으로 보지 않는다.

### G3. 이상 발견 뒤의 지속 추적

활성 업무에는 책임자가 있고 이상은 담당자에게 연결하도록 이미
정의됐다. 닫힌 업무에서 새 의무가 생기는 경우는 G1로 처리한다.
모든 관측 이상에 새 접수 객체·상태 체계·Agent 실행을 요구하지 않는다.

### O2. 포장 불일치와 정산

원 반례는 정상 규격90과 다른 포장10을 같은 항목의 수령100으로
합산했다. D02의 거래 품목·포장 구분과 D19의 항목별 대조를 이미
위반하므로 공격자는 반례를 철회했다.

물리 수령량과 계약상 인정량이 다른 실제 사례는 남는다. 예를 들어
확인된 계약이 적합 인수량에만 대금을 인정한다면 같은 품목에서도
품질 보류·거부가 정산 조건에 영향을 줄 수 있다. 이는 기존 별도
정산 목표에 계약 조건을 적용할 정책 사례다. 일반적인 지급채무 인식
규칙이나 새로운 회계 모델을 이 검토로 도입하지 않는다.

### 기존 조항이 방어한 추가 공격

- 동량 포장의 자동 대체: D02 v0.2가 이미 금지한다.
- 분할 운송40을 곧바로 분실로 판정: D14가 이미 금지한다.
- 최신 측정값이 무조건 정답: D14가 유효 결과 채택과 정정을 구분한다.
- 출고50, 고객 인수35를 인도50으로 판정: D17·D12의 증거 조건 위반이다.
- 반품25와 그 물량의 폐기25를 회수50으로 집계: D04·D12·D18의
  실제 물량·중복 집계 금지로 이미 배척된다.
- 경량 활동 기록은 반드시 Work Item/Run: D14가 명시적으로 분리한다.
- 파생 요약에는 비동기 projection 인프라가 필수: 동기 조회 계산으로도
  제안을 충족할 수 있으므로 근거 없는 요구다.

## 가장 작은 구현 방향과 검증의 한계

권고하는 최소 구성은 다음과 같다.

1. 운송·수령에 연결되는 타입 있는 관측 목록과 정정 참조.
2. 상위 업무에 정의된 기대 범위와 완료 증거 조건.
3. 요청 시 계산하는 현재 요약과 판단 당시 입력·규칙의 추적.
4. 기존 담당 업무가 이상을 추적하고 필요할 때만 추가 업무를 생성.
5. 실제 재고 쓰기·예약 대체·외부 연동·버전 전환마다 구체적인 계약 적용.

`AgentWorkService.java:48–54,95–105`의 현재 자식 업무 API는 Agent
역할과 Run 생성에 결합돼 있다. 그렇다고 저장된 모든 Work Item이
Run을 반드시 생성하는 것은 아니다. `DispatcherService.java:182–188`의
인간 담당 경로와 기존 follow-up 관찰·Attention 연결은 구별된다.
일반 측정·조사 기능이 이미 구현됐다고 해석해서도 안 된다.

검토는 4개 agent의 2라운드와 coordinator 통합으로 수행했다.
반대자가 철회한 주장은 결함 수에 남기지 않았다. 실행 테스트,
성능·비용 벤치마크, 법규 적합성 검증, 실환경 UAT는 수행하지 않았다.
다음 문서 확인만 실행했다: D01–D26 보존, Markdown 구조, 로컬 링크,
기준선 해시, 보고서의 주장 ID·반론·판정 대응.

본 결과는 “구현해도 안전하다”는 인수 판정이 아니다. 혼합안의
