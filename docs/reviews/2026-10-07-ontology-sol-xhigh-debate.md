별도 권리 엔진이나 새 테이블을 요구하지 않는다. 기존 계약 조건·

## C5. 활성 부모 없는 새 관측과 책임의 인수

근거: D10 992–1001행, D14 1182–1185·1209–1214행,
D26 1598–1605행, 채택된 이전 G1 1694–1696·1721–1723행.

### 공격과 이전 방어의 한계

조달 업무가 종료된 재고에 정기 창고 관측이 새 온도 이탈을 발견한다.
적용 정책상 조사나 품질 판단이 필요하다고 확인됐다고 가정한다.
이것은 과거 증거의 정정이 아니며 활성 조달 부모 업무도 없을 수 있다.

이전 보고서 G3의 “활성 부모 책임이 있다”는 방어만으로 이 사례를
처리할 수는 없다. 따라서 그 설명의 적용 범위를 활성 부모가 있는
관측으로 좁힌다. 이전 G1의 종료 후 정정 책임 보완은 그대로 유지한다.

### 현재 설계가 제공하는 방어와 의견 차이

D14는 담당·후속 행동이 필요하면 업무를 만들 수 있고, D10은 활성
업무의 주 책임자를 요구한다. D26도 책임 공백을 탐지하고 담당자에게
전달한다. 새 대응 업무를 표현할 수 없다는 구조적 결함은 아니다.

쟁점은 “대응 의무가 확인됐지만 아직 담당 업무가 인수하지 않은 구간”의
책임이다. 실행 reviewer는 생성 후 책임과 알림 전달만으로 연결 전의
지속 책임이 명시되지 않는다며 한때 좁은 의미 보완을 요구했다. 다른
reviewer들은 기존 규칙을 연결하는 구현·인수 계약으로 처리할 수
있다고 반론했다.

목표 reviewer도 한때 KEEP을 제안했지만, 필요한 업무 경로를 누락한
구현의 문제라는 반론을 받아 DOWNGRADE로 수정했다. 식별 reviewer는
신규 업무에 담당자를 즉시 배정할 수 있으며 기존 책임 인계의 수락
절차를 모든 초기 배정에 강제할 필요는 없다고 반론했다. 어느 방식이든
책임 연결이 완료되지 않은 의무를 방치하지 않는다는 결과는 같아야 한다.
실행 reviewer도 이 마지막 반론을 받아 DOWNGRADE로 수정했다. C5의
독립 결함 주장은 최종적으로 남기지 않는다.

### 최소 명료화 제안과 인수 사례

> 관측·새 사건·정정에서 현재 유효한 대응 의무가 확인되면, 담당이 배정된
> 업무로 연결한다. 기존 책임의 인계라면 인수 조건도 확인한다. 연결 전에는
> 지정된 접수 책임이 남으며 알림 전송만으로 의무를 해결 처리하지 않는다.

조달이 종료돼도 위 사례의 대응 담당자·다음 행동·확인 시점을 조회할
수 있어야 한다. 전달 실패나 담당 미수락으로 책임 연결이 끝나지 않은
경우도 미해결로 드러나야 한다. 접수 주체를 어느 조직·담당자로 정할지는
구축 정책이다. 모든 측정에 Work Item이나 Agent Run을 만들지 않는다.
정상 관측이나 추가 의무가 없는 차이는 근거를 남기고 종료할 수 있다.

## C2–C4. 기존 조항이 방어한 공격과 인수 사례

### C2. 누적 사건량과 시점 상태량

월요일60 도착 후 화요일60을 출고하고 수요일40이 도착했다면 누적

309–316행), 실제 결과 상태(179–186행), 재고량 구분(1298–1302행)을
적용하면 둘을 같은 목표 증거로 사용할 수 없다.

수요일까지의 누적 도착100 목표는 충족할 수 있다. 수요일 지정 시점의
사용 가능 재고100 목표는 충족하지 않는다. 이 두 목표를 동일 fixture로
검증한다. 시간 조건을 업무별로 구체화할 필요는 있지만 새 목표 엔진이나
독립 개념 결함을 도출하지 않는다.

### C3. 일반 역할 권한과 현재 요청의 범위

D08은 위임한 업무·대상·행동·기간을 지정하고(939–942행), D20은 서버
검증과 원문–해석–실행–결과 연결을 요구한다(1413–1421행).
D25는 실제 DB 효과와 자연어 의미를 평가한다(1559–1568행).

인수는 두 층으로 나눈다. 서버 계약에서는 사용자 역할이 쓰기를
허용해도 해당 Agent 위임이 조회만 허용하면 쓰기를 거부해야 한다.
모델 평가에서는 조회 요청이 쓰기 의도로 변환되지 않는지 확인한다.
후자의 의도를 서버가 자유문장만으로 완벽히 증명한다고 가정하지 않는다.
Agent가 스스로 주장한 위임 범위만 믿어서도 안 된다. 구체적인 위임
발급·검증 경로는 구현 계약이며 모든 쓰기에 인간 승인을 추가하지 않는다.

### C4. 새로운 실제 사건과 과거 증거의 정정

정상 인도100 뒤 실제 반품20이 발생한 것과 과거 인도100 기록이 사실98로
정정된 것은 다르다. D06의 사건·기록 시각과 정정(865–869행),
D17의 반송 연결(1332–1335행), D18의 반품 업무(1359–1363행)가
그 차이를 표현한다.

첫 사례는 과거의 정상 인도 사실을 보존하고 확인된 계약에 따라 현재
반품·대체·정산 의무를 연결한다. 두 번째는 과거 판정을 보존하면서
정정된 증거로 목표를 재평가하고 현재 남은 의무를 추적한다. 두 경우
모두 이전 업무를 무조건 재개하거나 아무 후속 의무 없이 자동 종료하지 않는다.

## 전체 범위 확인과 검증의 한계

| 범위 | 함께 대조한 경계 |
|---|---|
| D01–D08 | 포함 범위, 거래·포장 동일성, LOT·물량·계보, 단위·보존, 위치·소유, 상태·시간, 활동·문서, 주체·위임 |
| D09–D12 | 목표 끝점, 책임·수락 인계, 변경·대기·종료, 독립 수요 배분, 증거와 시간별 판정 |
| D13–D19 | 승인·약속·부분 이행, 운송·관측, 기관/QC 제한, 적격·예약·출고, 인도, 반품·회수·처분, 정산 |
| D20–D24 | 요청 의미·권한, 버전 의미와 현재 정책, 원천별 사실·정정, 저장·전환 경계, 접근·감사 |
| D25–D26 | 의미·업무 효과 평가, 인수와 완전성 증명의 차이, 운영 책임, 불명확한 외부 결과와 복구 |

이전 I1의 실물 식별 가능성과 G1의 종료 후 정정 책임은 이미 채택한
전제로 적용했다. I2/O1/P1/P2의 재고 정정·대체 예약·실행 버전·외부
기록 식별 계약은 계속 구현 전 과제이며 새 결함으로 집계하지 않았다.

실행한 확인은 기준선 해시, 원문 보존, D01–D26의 존재, 주장과 판정의
대응, Markdown 구조·로컬 링크·공백 검사다. 위 수치·상태 사례는
실행된 테스트가 아니라 논리적 반례와 후속 인수 제안이다.

코드 변경, DB 변경, 테스트 실행, 실제 모델 업무 UAT, 성능·비용 측정,
법규 적합성 검증은 수행하지 않았다. 사례의 판매 허용·정산·대응 의무는
명시한 가정이다. 시작 시 보드 조회는 GitHub token의 `read:project`
scope 부족으로 실패했다. Phase·이슈·보드 상태를 변경하거나 현재
상태가 확인됐다고 주장하지 않는다. 이번 작업은 설계 조사·검토 범위다.

## 후속 적용 기록 (2026-10-07)

검토 후 사용자의 “보완하고 끝내라” 지시에 따라 C1–C5를 설계 본문의
관련 D 항목과 D25 인수 사례에 반영했다. 적용 내역과 완료 범위는
[논의 기록](../ontology-discussion.md) §12를 따른다. 위 제안·판정·해시와
행 번호는 검토 당시의 기록이며, 본문 보완 후 문서는 당시 동결본과
다르다. 문서 보완 완료를 테스트 실행이나 구현 인수 완료로 해석하지 않는다.
