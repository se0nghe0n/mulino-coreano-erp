# 식품 수입·유통 온톨로지 논의 기록

작성일: 2026-10-06 (Asia/Seoul)
최종 갱신: 2026-10-07 (Asia/Seoul)

현재 상태: Sol 검토 보완의 본문 반영 완료. 기본안의 채택 범위는 §10, 이번 보완의 적용과 완료 범위는 §12를 따른다. 현재 설명은 [철학과 워크플로우 통합 설명서](ontology-design-philosophy.md)에서 읽는다. 이 문서는 제안·코멘트·결정·검토·변경의 이력을 보존한다.

## 문서의 역할

이탈리아 제과 상품을 국내로 수입해 유통하는 업무를 설명할 온톨로지의 논의를 누적한다. 이후 논의도 이 문서에 반영한다.

사용자가 명시한 방향과 설계 제안, 미정 사항을 구분한다. 이 문서는 구현 명세나 개발 착수 결정이 아니다. 기존 업무 문서, DB 구조와 프로젝트 보드의 범위를 자동으로 변경하지 않는다. 구현 목표로 전환할 때는 기존 이슈와 대응시키고 범위를 정한다.

## 1. 합의한 방향

### 1.1 업무 범위

주요 업무는 이탈리아에서 제조된 제과 상품을 한국으로 수입하고 국내 거래처에 유통하는 과정이다. 국내 제조 중심의 기존 데이터 구조를 그대로 온톨로지의 정의로 삼지 않는다.

상품의 정체성, 수량, 위치, 책임, 공급 가능 여부와 그 근거를 연결한다. 국내 제조·가공이나 재포장은 필요성을 확인한 뒤 별도로 범위를 정한다.

### 1.2 품사를 활용한 개념 설계

문법적 품사를 엄격히 적용하기보다 다음 질문으로 개념을 찾는다.

- 명사형: 무엇인가. 독립적으로 식별하는 대상이다.
- 형용사형: 어떠한가. 대상의 속성·상태를 설명한다.
- 동사형: 무엇을 하거나 겪는가. 활동·업무·관계를 설명한다.

대상을 식별하면 형용사형 설명과 동사형 활동·관계를 연결해 그 대상의 성질, 상태, 이력과 근거를 설명할 수 있어야 한다.

품사 분류 자체가 테이블이나 클래스의 일대일 설계를 뜻하지는 않는다. 단순 속성값과 독립적인 이력·증거가 필요한 기록을 구별한다.

명사형 대상뿐 아니라 동사형 업무도 관리의 시작점으로 제공한다. 두 진입점은 동일한 대상·활동·목표와 관계를 공유한다.

### 1.3 제한된 유연성

정의된 속성을 대상에 선택적으로 부여할 수 있도록 한다. 새 속성·관계·동사의 정의는 제한적으로 허용한다.

사용자의 자연어 표현은 다양하게 받되 Agent와 시스템 사이에는 의미가 정의된 통제 어휘를 사용한다. 실제 LOT 번호, 수량, 날짜를 사전에 모두 열거한다는 뜻은 아니다.

구축 시 사전을 정의하는 기능은 FDE가 사용하는 고급 기능으로 둔다. 구축 후 정의 변경은 제한하고 운영 중 변동 가능성을 줄인다. 운영 Agent가 새로운 의미나 관계를 임의로 만들어 저장하지 않는다.

### 1.4 의미와 업무 결과를 검증하는 테스트

같은 의미의 사용자 요청이 일관된 조회로 이어지는지, 모호한 입력이 잘못된 저장으로 이어지지 않는지 테스트한다. 문구나 SQL 문자열의 일치보다 해석된 대상·조건과 실제 업무 결과를 검증한다.

### 1.5 업무 동사는 목표를 가진다

사용자가 요청하는 업무에는 달성해야 할 지점이 필요하다. 이번 논의에서 “발주하다”는 발주서 생성으로 끝나지 않는다. 목표한 지점에 필요한 물건이 도착하는 것이 업무 목표다.

활동 완료와 목표 달성을 구분한다. 발주서 전송, 운송사 인계 등이 끝났더라도 목표 물량이 도착하지 않았다면 남은 책임을 유지한다. “발주”의 이 의미는 이 프로젝트에서 합의하는 업무 해석이며, 일반적인 발주 용어의 정의 전체를 대체하는 주장은 아니다.

### 1.6 통사론 관점에서 읽는 설계의 중심

§1.2의 명사형 대상·형용사형 설명·동사형 개념을 정의하고, §4와 D07의 허용 대상·관계·필수 조건으로 결합한다. 이렇게 구성한 사실·조회·활동· 목표 업무를 같은 의미로 다루는 것이 설계의 중심이다. 실제 수입·유통 흐름은 이 공통 원리를 적용하는 업무 범위다.

“비스킷100상자를 금요일까지 W에 도착하도록 발주한다”는 품목·수량· 장소·기한·동사·목표 끝점으로 연결할 수 있다. 문장이 구조적으로 성립하더라도 대상 식별, 증거에 따른 사실·목표 판정, 위임·행동 권한은 각각 검증한다. 관계·활동·목표 업무를 모두 같은 실행 단위로 만들지 않는다.

이 설명은 기존 §1.2–§4, D07·D09·D20·D21의 연결을 드러낸다. 자연어 품사를 테이블에 일대일 대응하거나 형식 문법·파서·AST·새 DSL을 도입하기로 한 결정은 아니다. [통합 설명서](ontology-design-philosophy.md)의 1–6장에서 설계 철학을 설명하고, 7–12장에서 같은 철학으로 업무 흐름을 따라간다.

## 2. 논의 중인 개념 구조

아래 세부 구조와 명칭은 설계 제안이다. 아직 확정된 스키마가 아니다.

### 2.1 명사형 대상

| 대상 | 의미 |
|---|---|
| 품목 | 주문·판매·재고 관리에 사용하는 상품 규격 |
| 제조 LOT | 제조자가 구분한 생산 배치 |
| 추적 물량 | 위치·이동·판정을 구별해 관리할 물품 범위 |
| 물류 단위 | 상자·팔레트 등 실제 보관·운반 단위 |
| 장소 | 출하장·창고 등 위치와 활동 발생 장소 |
| 행위 주체 | 제조사·수입사·운송사·담당자 등 |
| 업무 문서 | 발주·운송·신고·검사 등의 정보 기록 |
| 결정 | 근거에 따라 행위를 허용하거나 제한하는 판단 |
| 목표 | 업무가 달성해야 하는 결과와 조건 |

SKU는 품목의 식별자다. 소매 포장·묶음 상자는 포장 규격 또는 물류 단위이며 제조 LOT와 구별한다. LOT 번호는 제조자·품목 등의 문맥 없이 전 세계적으로 유일하다고 가정하지 않는다.

추적 물량을 하나의 품목·제조 LOT에 속하게 하고, 여러 LOT를 담은 팔레트는 그 물량들을 묶는 구조를 제안했다. 추적 물량의 식별과 분할·합침 정책은 아직 확정하지 않았다.

### 2.2 형용사형 설명

속성·상태는 적용 대상을 명확히 한다. 동일 SKU라도 일부 물량은 운송 중이고 다른 물량은 창고에 있을 수 있다.

설명은 다음 형태를 기본으로 검토한다.

```text
대상 — 속성 — 값
필요한 문맥: 단위, 적용 시점, 적용 범위, 출처, 근거
```

내용량처럼 단순한 속성값과 품질 보류처럼 판단자·시점·근거가 필요한 상태 기록을 구분한다. 위치, 물류 진행, 수입 업무 진행, 품질 상태를 하나의 상태값으로 합치지 않는다.

속성이 없다는 사실을 “문제없음”이나 “해당 없음”으로 해석하지 않는다. 서로 다른 관찰값은 필요한 경우 시점·출처별로 보존한다.

### 2.3 동사형 개념

| 구분 | 예 | 의미 |
|---|---|---|
| 관계 | LOT에 속하다 | 대상 사이의 연결 |
| 활동 | 발주서를 전송하다 | 시점·참여자·결과가 있는 사건 |
| 목표를 가진 업무 | 필요한 물품을 발주하다 | 결과 달성까지 책임지는 과정 |

동사 유형과 개별 실행을 구별한다. “운송”은 활동 유형이고, 특정 물량을 특정 시점에 이동시킨 운송은 개별 활동이다. 항공·육상은 운송 방식으로 표현할 수 있다.

관찰·판단·허용도 구별한다. 검사가 수행됐다는 사실은 합격이나 출고 허용을 자동으로 뜻하지 않는다.

## 3. 목표 중심 업무 설계

현재 논의의 초점이다. 세부 필드와 완료 판정 규칙은 제안 상태다.

### 3.1 목표의 구성

| 구성 | 정의할 내용 |
|---|---|
| 대상 | 어떤 품목·규격의 물건인가 |
| 수량 | 얼마나 필요한가. 단위는 무엇인가 |
| 지점 | 어디에 도착해야 하는가 |
| 시점 | 언제까지 필요한가 |
| 완료 조건 | 어떤 사실이 성립하면 달성인가 |
| 완료 증거 | 무엇으로 그 사실을 입증하는가 |
| 책임자 | 달성 또는 명시적 종료까지 누가 책임지는가 |
| 제약 | 승인된 구매 조건 등 무엇을 지켜야 하는가 |

예시는 “비스킷 100상자가 기한까지 창고 W에 도착하고 수령 사실이 확인된다”이다. 수령 확인을 완료 증거로 사용하는 안을 제안했다. 도착·수령·사용 가능은 별개이며 품질 허용까지 목표에 포함할지는 업무별로 명시해야 한다.

### 3.2 목표와 계획·활동·증거

```text
목표
 ├─ 달성 조건과 책임
 ├─ 달성하기 위한 계획
 │   └─ 승인·주문 전달·출하·운송·수령 등의 활동
 └─ 달성 여부를 입증하는 결과와 증거
```

한 번의 운송을 두 번의 분할 운송으로 바꾸더라도 목표는 유지될 수 있다. 수량·기한·목적지를 바꾸는 것은 목표 변경으로 다루고 결정과 이유를 남기는 방향을 제안했다.

100상자 중 60상자를 수령했다면 남은 40상자의 후속 업무와 책임을 유지한다. 지연·수량 불일치·증거 부족이 있으면 전체 완료로 처리하지 않는다. 목표 취소·대체·부분 수용의 권한과 절차는 미정이다.

### 3.3 형용사형 상태와의 연결

업무 동사의 목표를 검증 가능한 결과 상태로 표현한다.

- 운송: 대상 물량이 목적지에 도착한 상태를 목표로 삼을 수 있다.
- 검사: 대상에 대한 검사 결과가 기록된 상태를 목표로 삼을 수 있다.
- 조달: 필요한 물량이 합의한 수령 조건을 충족한 상태를 목표로 삼는다.

목표 상태는 실제 결과·증거로 확인해야 한다. Agent의 완료 보고나 상태 문자열만으로 달성을 확정하지 않는다.

### 3.4 목표 책임과 활동 수행의 구분

다음은 후속 논의를 위한 제안이다. 조직별 담당자나 권한을 확정한 것은 아니다. 아래 역할은 책임의 종류이며 반드시 서로 다른 사람을 뜻하지 않는다. 겸임 허용 여부는 업무별로 정한다.

| 역할 | 책임 |
|---|---|
| 목표 책임자 | 전체 달성 여부와 미완료 사유를 추적하고 후속 대응을 연결한다 |
| 활동 수행자 | 위임받은 활동을 수행하고 결과·예외·증거를 보고한다 |
| 완료 판정 역할 | 목표 조건과 증거를 대조해 충족·미달·미확인을 판정한다 |
| 목표 변경 승인 역할 | 수량·기한·목적지 변경 또는 취소를 결정한다 |

업무 위임은 특정 활동의 수행을 넘기는 것이다. 운송사에 운송을 맡겼다는 이유만으로 발주 목표 책임이 자동 이전되지는 않는다. 목표 책임의 인계는 별도 기록으로 다루고 인수 주체, 효력 시점, 남은 의무와 진행 상태를 확인하는 방향을 제안한다. 인계 요청만으로 기존 책임을 해제하지 않는다.

Agent는 위임된 범위에서 활동을 조정하거나 수행할 수 있다. 실행 세션이나 Run의 종료를 업무 목표의 종료로 해석하지 않는다. 목표 책임은 세션을 넘어 유지되는 업무 기록에 연결한다.

### 3.5 활동 결과와 목표 달성의 관계

```text
목표 G: 기한까지 창고 W에 비스킷 100상자 도착
 ├─ 목표 책임: 담당 역할 또는 지정 주체
 ├─ 활동 A: 발주 승인·전달 → 구매 담당
 ├─ 활동 B: 출하·운송 → 공급자·운송 담당
 ├─ 활동 C: 도착·수령 확인 → 창고 담당
 └─ 완료 판정: 목표 조건과 실제 결과·증거 대조
```

활동 완료를 모두 합친 것만으로 목표 달성을 증명하지 않는다. 중복되거나 다른 물량에 대한 증거, 잘못된 장소의 수령 기록은 목표를 충족하지 못한다. 수령 기록을 도착 증거로 인정하는 조건도 별도로 정해야 한다.

한 활동이 실패해도 다른 운송이나 공급 방법으로 목표를 달성할 수 있다. 대안의 추가 비용·구매 변경 등은 기존 권한과 승인 범위를 따른다. 대안을 검토하는 것과 실행하는 것을 구분한다.

### 3.6 미달과 예외를 표현하는 사례

| 관찰한 결과 | 목표에 대한 해석 | 이어갈 책임 |
|---|---|---|
| 발주서 전송 완료, 도착 없음 | 전송 활동 완료, 도착 목표 미달 | 이행·출하·운송 추적 |
| 조건에 맞는 60상자 도착 | 수량 기준 60 충족, 40 미달 | 나머지 물량의 공급과 기한 확인 |
| 운송 취소 | 해당 활동 실패, 목표 달성 가능성 재평가 | 대안과 승인 필요 여부 검토 |
| 도착 주장만 있고 증거 부족 | 완료 여부 미확인 | 증거 확보와 판정 |
| 기한이 지난 뒤 100상자 도착 | 수량·지점 충족, 기한 미충족 | 지연 영향과 후속 결정 기록 |

목표 조건별 충족 여부와 업무 처리 상태를 구분한다. 취소·종료된 업무가 목표를 달성한 것은 아니다. 뒤늦은 도착으로 과거의 납기 위반을 지우거나, 새 기한으로 기존 목표를 덮어써 성공으로 만들지 않는다. 변경 목표는 이전 조건·결정 이유와 연결해 보존하는 방향이다.

### 3.7 완료 증거와 판정의 초안 (D12)

목표를 만드는 시점에 완료 조건과 그 조건을 입증할 증거의 종류를 함께 정하는 방안을 제안한다. Agent의 보고는 근거를 가리키는 설명이며, 그 자체로 물리적 도착을 확정하는 증거라고 간주하지 않는다.

증거를 평가할 때 다음을 확인한다.

| 관점 | 확인할 내용 |
|---|---|
| 대상 | 목표 품목·규격·해당 공급 물량과 연결되는가 |
| 수량 | 동일 단위 또는 승인된 환산 기준으로 비교 가능한가 |
| 장소 | 목표 지점의 도착·수령을 입증하는가 |
| 시점 | 기록 입력 시각이 아니라 실제 사건 시각이 조건에 맞는가 |
| 출처 | 해당 사실에 대해 인정된 기록 주체·원천인가 |
| 유효성 | 중복·취소·정정·상충 여부와 적용 범위가 확인됐는가 |

수령 기록을 도착 증거로 인정하는 목표의 예를 사용한다. 실제로는 도착만 요구하는지, 창고 인수까지 요구하는지에 따라 증거가 달라진다. 물류사의 배송 완료 메시지와 창고 수령 기록 중 어느 것을 인정할지도 해당 목표의 증거 정책으로 정해야 한다. 외부 보고는 이름만으로 항상 인정하거나 배제하지 않는다.

예: 목표는 기한까지 창고 W에 비스킷 100상자 도착이다.

- 기한 내 W에서 확인된 60상자 기록은 수량 60을 뒷받침한다.
- 같은 60상자에 대한 운송사 기록을 추가해도 120으로 합산하지 않는다.
- 다른 창고 V의 40상자 도착은 목적지 W 조건을 충족하지 않는다.
- W의 나머지 40상자가 기한 뒤에 도착하면 총량 도착과 납기 미충족을 함께 기록한다. 이를 원래 목표의 완전한 달성으로 표현하지 않는다.

증거 부족과 실제 미달을 구별한다. 도착 기록이 없다는 이유만으로 실제 미도착을 확정하지 않는다. 조건별 판정에 `충족`, `미충족`, `미확인`을 구분하고 상충하는 증거의 존재도 별도로 표시하는 안이다.

구조화된 기록으로 모든 조건이 확인되면 자동 판정할 수 있다. 상충·식별 불확실성·예외 허용이 필요하면 정해진 담당자에게 판단을 요청한다. 구체적인 자동 판정 범위와 권한은 아직 미정이다.

판정에는 목표 버전, 증거 참조, 적용 규칙 버전, 판정 시점과 주체를 남기는 방향을 제안한다. 나중에 증거가 정정되면 이전 판정을 보존하고 영향받은 목표를 재평가한다. 재개·통지 절차는 D11·D26에서 정한다.

### 3.8 동사의 기본 목표와 개별 업무 목표 (D09)

D12의 완료 증거·판정 논의를 바탕으로 다음 항목으로 이동한다. 다음은 세부 설계 제안이며 새로운 필드와 절차가 확정된 것은 아니다.

동사의 업무 정의와 실제 요청에서 만들어진 목표를 구분한다.

| 구분 | 정의하는 내용 | 발주 예시 |
|---|---|---|
| 업무 유형 | 필수 조건, 선택 범위, 완료·증거 규칙 | 목표한 지점의 물품 도착을 확인한다 |
| 개별 목표 | 이번 요청의 대상·값·끝점 | 비스킷 100상자를 특정 날짜까지 W에 도착시킨다 |
| 수행 계획 | 목표에 도달하는 방법 | 공급자와 운송 구간, 분할 배송을 정한다 |

업무 유형은 채울 항목과 허용 범위를 제시한다. 개별 목표는 그 범위 안에서 이번 요청의 값을 확정한다. 계획은 목표 조건을 지키는 범위에서 바뀔 수 있다. 계획 변경이 비용·권한·승인 범위를 바꾸면 별도 검증이 필요하다.

개별 목표의 기본 항목으로 다음을 제안한다.

- 대상: 식별된 품목과 규격. LOT 지정 필요 여부는 업무에 따른다.
- 수량: 수치와 단위, 허용 오차가 있다면 명시된 기준.
- 지점: 도착 장소의 식별자와 필요한 상세 범위.
- 기한: 달력상의 시점과 시간대. 미정과 기한 없음은 구분한다.
- 끝점: 도착, 수령 확인, 사용 가능 중 요청한 업무의 끝.
- 증거 정책: 해당 끝점을 입증할 출처·범위·중복 배제 조건.
- 제약: 구매 조건, 예산, 대체 허용 등 해당 업무에 필요한 제한.
- 책임: 추적 책임과 적용되는 권한 정책.

목표마다 사람이 모든 항목을 반복해서 입력하도록 요구하지 않는다. 요청의 명시값, 식별된 거래·조직 문맥, 승인된 기본값에서 채울 수 있으나 값의 출처를 남긴다. 사용자 지정값이 고정 제약을 무효화하지 않는다. 상충하거나 업무 결과를 바꾸는 정보가 부족하면 확인한다.

예를 들어 “평소처럼 비스킷 100상자를 발주해 줘”에서 품목·창고· 기한을 과거 한 사례만으로 단정하지 않는다. 유효한 기본값과 문맥으로 결정할 수 있는 항목은 채우고 해결되지 않은 항목만 확인한다. LOT를 선적 이후에 배정하는 업무라면 접수 시 LOT 미정 자체를 오류로 취급하지 않는다. 각 정보가 필요한 시점을 별도로 정한다.

목표 해석의 확정과 구매 실행의 승인은 구분한다. 모든 목표 등록에 새로운 인간 승인을 요구하는 정책은 제안하지 않는다. 기존 권한과 해당 활동의 승인 규칙을 적용한다.

비교 예시는 다음과 같다.

- 목표 유지: 기한·품목·수량·지점·끝점을 지키면서 100상자를 60상자와 40상자로 나눠 운송한다. 분할 허용 조건도 확인한다.
- 목표 변경: 100상자를 80상자로 줄이거나 기한·목적지를 바꾼다. 원래 조건과 변경 결정·적용 범위를 보존한다.
- 끝점 차이: 도착 목표를 달성해도 품질 사용 허용까지 달성한 것은 아니다. 반대로 사용 가능 재고 확보 목표는 도착만으로 완료하지 않는다.

검증 사례는 필수값 누락, 기한 미정과 없음의 구별, 기본값의 출처, 고정 제약과 요청의 충돌, 계획 변경과 목표 변경의 구분을 포함한다.

### 3.9 명사와 동사를 통한 두 가지 진입점

사용자는 품목 명사뿐 아니라 동사도 관리의 시작점이 될 수 있어야 한다고 제시했다. 하나의 모델에 대상 중심과 업무 중심 진입점을 둔다. 별개의 데이터 체계를 만들거나 품목 중심 접근을 폐기하는 뜻은 아니다.

- 대상 중심: 품목·LOT·물량을 먼저 식별하고 관련 상태·활동·목표를 찾는다.
- 업무 중심: 발주·운송·검사 등의 업무를 먼저 선택하거나 식별하고, 목표와 필요한 대상·조건을 연결한다.

세부 설계로 업무 유형, 개별 업무, 수행 활동을 구분하는 안을 제안한다. “발주하다”는 유형이고 “이번 비스킷 100상자 발주 업무”는 개별 업무다. 개별 업무는 목표를 가지며 계획과 실행 활동에 연결된다.

업무부터 시작해도 물품 대상을 생략하지 않는다. 대상이 불분명하면 요청·초안에 확인 필요 사항을 남기고, 해당 쓰기에 필요한 식별이 갖춰진 뒤 실행한다. 구매 접수 시 품목은 필요하지만 실제 제조 LOT는 공급 확정 이후 연결할 수 있는 것처럼 정보별 필요 시점을 정한다.

두 진입점은 같은 식별자와 관계를 사용한다. 품목 화면의 발주 업무와 업무 화면의 대상 품목은 같은 기록을 가리켜야 한다. 관계는 업무 유형에 따라 복수 대상을 허용할 수 있으므로 항상 일대일로 가정하지 않는다.

예: 품목에서 “진행 중인 발주”를 찾는 조회와 해당 발주 업무에서 “대상 품목”을 찾는 조회는 같은 업무-품목 연결을 반환해야 한다. 두 경로에서 같은 요청을 실행해도 별개의 업무·입고가 중복 생성되지 않도록 요청 식별·멱등성 계약을 적용하는 방향이다.

### 3.10 두 진입점이 공유하는 개별 업무

§3.9를 구체화하는 설계 제안이다. 개별 업무를 지속적으로 식별하고 대상·목표·책임·활동을 연결한다. 기존 Case·Work Item·Run과의 일대일 대응이나 새로운 DB 테이블을 여기서 확정하지 않는다.

| 구성 | 기록할 내용 |
|---|---|
| 업무 식별 | 업무 ID와 유형, 접수 요청·문맥 |
| 목표 | 달성 조건과 목표 버전 |
| 대상 항목 | 품목·수량·단위·목적지·기한 등 항목별 조건 |
| 참여·책임 | 해당 업무에서의 역할, 적용 범위·기간, 위임·인계 |
| 계획·활동 | 수행 방법, 의존성, 담당자, 실제 결과 |
| 근거·판정 | 활동·물량별 증거와 조건별 충족 판정 |
| 후속 조치 | 미완료 이유, 다음 행동·담당·확인 시점 |

한 업무가 여러 품목이나 물량을 대상으로 할 수 있으므로 대상 항목별 목표를 구분한다. 전체 완료가 모든 항목의 충족을 요구하는지, 부분 수용을 허용하는지는 목표 계약에서 정한다. 여러 업무를 한 번에 운송하더라도 물량 배분을 구분하고 같은 수령량을 중복 충족으로 사용하지 않는다. 상위 목표와 하위 목표가 같은 증거를 참조하는 것과 독립된 수요 두 건에 같은 물량을 중복 배정하는 것은 구별한다.

예: 업무 W-001의 목표는 비스킷 100상자를 기한까지 창고 A에 도착시키는 것이다. 기한 내 60상자 도착이 확인되면 대상 항목의 미달 수량은 40상자다. 나머지가 운송 중이면 운송 활동, 도착 예정, 다음 확인 담당을 연결한다. 사용자가 품목으로 조회해도 W-001로 조회해도 같은 물량·활동·판정을 보여야 한다.

조직의 일반 역할과 개별 업무의 실제 책임 배정을 구별한다. “구매 담당”이라는 역할이 존재하는 것만으로 W-001의 담당자가 정해지는 것은 아니다. 업무별 담당 주체를 지정하거나 해당 업무에 적용된 배정 정책의 결과를 기록한다. 담당자가 비어 있으면 책임 공백으로 드러내야 하며 책임이 있는 것처럼 표시하지 않는다.

업무의 처리 상태와 목표 조건의 판정을 분리한다. 예를 들어 운송 결과를 기다리는 업무는 처리 상태가 대기여도 60상자 도착 사실을 유지한다. 취소로 종료된 업무는 달성으로 표시하지 않는다. 구체적인 상태명·전이는 D11에서 정한다.

새 요청과 기존 업무를 연결할 때 다음을 제안한다.

- 명시적 업무 참조와 확인된 대화 문맥으로 기존 업무를 찾는다.
- 같은 품목·수량이라는 이유만으로 서로 다른 주문을 합치지 않는다.
- 같은 요청의 재전송은 요청 식별·멱등성 계약으로 중복을 막는다.
- 추가 주문인지 기존 업무의 변경인지 모호하면 실행 전에 확인한다.
- 화면·대화·실행 세션이 바뀌어도 같은 업무 ID를 사용한다.

“비스킷 40상자를 더 보내 달라”는 요청은 기존 부족분의 운송 요청, 기존 목표의 수량 증가, 독립된 새 주문일 수 있다. 이를 문장만으로 단정하지 않고 업무 문맥과 변경 의도를 확인한다.

검증에는 두 진입점의 조회 일치, 합법적인 동일 품목의 별도 주문, 동일 요청 재전송, 변경과 신규의 모호성, 복수 품목의 일부 달성, 역할만 있고 실제 담당이 없는 업무를 포함한다.

### 3.11 업무의 시작·대기·재개·변경·종료 (D11)

아래는 처리 상태와 전이의 제안이다. 기존 구현의 enum이나 Case· Work Item 상태를 변경하는 결정은 아니다. 업무 처리 상태, 목표 조건별 충족 판정, 실행 활동의 결과를 서로 구분한다.

| 처리 상태 | 의미 |
|---|---|
| 초안 | 요청은 있으나 실행에 필요한 목표·대상·책임 등이 미확정이다 |
| 진행 | 현재 수행 가능한 활동이나 후속 판단이 있다 |
| 대기 | 다음 진행에 외부 사건·결정·시간 등의 조건이 필요하다 |
| 종료 | 해당 업무의 추적을 끝낼 사유와 잔여 책임 처리가 기록됐다 |

초안도 확인 담당과 미정 항목을 기록해 방치하지 않는다. 진행으로 전환할 때 해당 시점에 필요한 조건과 권한을 검증한다. 나중에 배정할 LOT처럼 현재 단계에 필요하지 않은 정보까지 모두 요구하지 않는다.

부분 도착, 기한 초과, 취소 요청은 목표나 사건의 사실이다. 이를 모두 별도 업무 처리 상태로 늘리지 않고 진척·예외·결정으로 연결한다. 목표 충족을 확인하기 전까지 처리 상태가 진행이나 대기일 수 있다.

#### 대기의 계약

대기는 업무 포기가 아니라 다음 진행 조건을 가진 책임 유지 상태다. 대기 기록에 다음을 두는 방향을 제안한다.

- 사유: 무엇 때문에 다음 활동을 진행할 수 없는가.
- 범위: 어느 업무·활동·대상 항목이 기다리는가.
- 재개 조건: 어떤 사실·결정·시점이 확인되면 진행할 수 있는가.
- 확인 책임: 누가 해당 조건을 확인하고 다음 행동을 연결하는가.
- 확인 시점·수단: 이벤트 수신 또는 다음 점검 시점과 미수신 대응.
- 기한 초과 대응: 누구에게 알리고 어떤 판단을 요청하는가.

예를 들어 나머지 40상자를 기다리는 업무라면 운송 참조, 대상 물량, 도착 확인 조건, 담당자와 다음 확인 시점을 연결한다. 단순한 예정일 도래나 공급자의 응답 수신만으로 도착 목표를 충족 처리하지 않는다. 기간 경과를 승인·수락으로 해석하지 않는다.

일부 활동이 대기 중이어도 다른 활동을 수행할 수 있으면 전체 업무는 진행 상태일 수 있다. 상위 업무를 대기로 표시하는 조건은 현재 실행 가능한 활동과 미충족 의존성을 함께 보고 정한다.

#### 재개와 재계획

재개 사건이 오면 해당 업무·활동·대상·목표 버전에 대응하는지 먼저 확인한다. 조건을 충족하면 진행으로 돌아가 필요한 활동을 수행한다. 중복·늦은 사건이나 이미 바뀐 계획의 응답이 업무를 잘못 재개하거나 중복 실행하지 않도록 검증한다. 과거 사건은 기록으로 보존할 수 있으나 현재 상태를 바꾸는 효과는 별도로 판단한다.

운송 취소 같은 활동 실패는 재계획 사유가 될 수 있다. 목표 달성이 불가능하다는 결론이나 목표 취소로 자동 연결하지 않는다. 대체 운송도 비용·권한·계약 조건의 허용 범위에서 실행한다.

#### 목표 변경과 종료

목표 변경은 처리 상태와 별도의 결정으로 남긴다. 변경 제안이 있다고 새 조건을 즉시 유효하게 만들지 않는다. 승인된 변경에는 효력 시점과 진행 중인 활동·계약·증거의 적용 범위를 기록한다. 변경 검토 중에 기존 활동을 계속할지 보류할지도 정책으로 정해야 한다.

종료 사유의 예로 목표 달성, 승인된 취소, 달성 불가 판단에 따른 중단을 검토한다. 단순 실행 오류나 Agent 세션 종료는 종료 근거가 아니다. 수량 충족·기한 미충족 같은 목표 판정은 종료 사유와 함께 보존한다.

종료 시 남은 운송·공급자 약속·비용·반품 등 의무를 확인한다. 목표가 취소돼도 이미 출하된 물품이나 외부 계약이 자동 취소되는 것은 아니다. 남은 의무는 권한 있는 결정으로 해소하거나 인수된 후속 업무로 연결한 뒤 원 업무를 닫는 방향을 제안한다. 책임 인계 없이 숨기지 않는다.

종료 뒤 증거 정정이 발생하면 기존 기록을 지우지 않고 재평가한다. 재개할지, 정정 후속 업무를 만들지, 통지만 할지는 영향과 권한 정책에 따라 정한다. 구체적인 기준은 미정이다.

#### 전이 사례와 검증 후보

```text
초안 → 진행: 현재 단계의 필수 조건·책임·권한 확인
진행 → 대기: 대기 조건·확인 책임·다음 점검 설정
대기 → 진행: 해당 범위의 조건 충족 또는 승인된 재계획
진행/대기 → 종료: 판정·종료 사유와 잔여 의무 처리 확인
```

이는 주요 경로의 예시이며 모든 전이를 열거한 실행 규칙은 아니다. 초안 취소와 종료 후 정정의 경로도 상세 설계에서 다룬다.

검증 후보는 대기 중 책임 유지, 알림만으로 승인하지 않음, 부분 활동 대기와 전체 진행의 구분, 중복·지연 사건, 실패 후 대체 계획, 취소 후 잔여 의무 인계, 지연 도착의 기한 미충족 보존, 종료 후 증거 정정이다.

### 3.12 업무 상태의 형용사형 표현과 업무 간 연결

사용자는 작업 상태를 동사의 형용사로 표현할 수 있다고 제시했다. 이를 개별 업무에 형용사형 설명을 부여하는 방향으로 반영한다. 동사 유형 자체와 개별 실행의 상태를 구별한다. 완료된 검사 업무와 품질 보류된 물량은 서로 다른 대상에 대한 설명이다.

업무에는 처리 상태·목표 진척·기한 상태가 함께 붙을 수 있다. “대기 중인 발주, 60상자 도착, 기한 초과”는 모순이 아니다. 종료됐다는 사실과 목표를 달성했다는 사실은 구분한다.

후속 설계 제안으로 업무 간 관계를 세 종류로 나눈다.

- 분해·기여: 하위 업무가 상위 목표의 어느 대상·수량·조건에 기여하는가.
- 의존: 어떤 선행 결과·증거가 다음 활동을 허용하는가.
- 공유: 하나의 운송·검사 활동이 여러 업무에 어떻게 배분되는가.

60상자와 40상자의 운송 결과를 합칠 때 같은 목표의 품목·지점·기한에 맞는지 검증한다. 해상 구간 완료가 최종 창고 도착을 뜻하지 않으며, 하위 업무가 모두 완료됐다는 보고만으로 상위 목표를 달성 처리하지 않는다. 한 운송이 여러 독립 주문을 담당하면 배분 수량 합계가 실제 해당 물량을 초과하지 않도록 한다. 책임도 주문별로 유지한다.

의존 조건은 선행 업무의 상태명보다 실제 결과·증거에 연결한다. 증거가 정정·취소·만료되면 영향받는 후속 업무를 재평가한다. 필수 법규·고정 정책은 목표에 명시되지 않았다는 이유로 생략하지 않는다. 구체적인 정책은 공식 근거와 적용 범위를 확인한 뒤 정한다.

## 4. 구축 사전과 실행 로직의 경계

통제 어휘 논의는 일단 마무리하고 업무 목표 논의로 이동했다. 아래는 재개 시 참고할 설계 제안이며 제품 구현 결정은 아니다.

- 사전: 개념의 의미, 동의어, 적용 대상, 관계 형태를 정의한다.
- 공통 검증: 대상 유형, 연결 개수, 값·단위, 필수값 등을 검사한다.
- 업무 코드: 재고 반영, 중복 방지, 승인, 트랜잭션을 처리한다.

직접 연결로 충분한 소속 관계와 수량·시점·범위가 필요한 배분·위치 관계를 구별한다. 모든 관계를 단순 연결 하나로 표현하지 않는다.

FDE는 제공된 제약과 업무 기능을 구성한다. 사전에 임의 SQL이나 실행 스크립트를 넣거나, 새 동사 등록으로 DB 쓰기 기능을 얻는 구조는 제안하지 않는다.

사전·제약·업무 기능 연결·테스트를 같은 버전으로 배포하고 Agent와 서버가 동일 버전을 사용하는 안을 제안했다. 정확한 변경 승인권자, 배포·전환·복구 절차는 미정이다.

## 5. 검증 사례 후보

테스트 필요성은 합의했다. 아래 사례와 테스트 분리는 제안이다. 이 문서를 작성하면서 테스트 코드를 추가하거나 실행하지 않았다.

- 같은 문맥의 동의 표현이 같은 의미의 조회로 변환된다.
- 발주량·선적량·수령량처럼 다른 개념은 구분해서 조회한다.
- 식별이 모호하거나 필수 정보가 부족하면 확인하고 쓰지 않는다.
- 미등록 어휘와 허용되지 않은 관계를 임의로 생성하지 않는다.
- 입고 기록으로 품질 허용·통관 완료를 추론하지 않는다.
- 여러 운송 구간에 연결된 같은 물량을 중복 합산하지 않는다.
- 포장 환산 근거가 없으면 단위별로 결과를 구분한다.
- 무권한 승인과 같은 사건의 중복 반영을 막는다.
- 발주서 생성만으로 도착 목표를 완료하지 않는다.
- 부분 수령 후 남은 수량과 책임이 유지된다.
- 활동 위임이나 인계 요청만으로 기존 목표 책임이 사라지지 않는다.
- Run 종료나 모든 활동의 완료 보고만으로 목표를 달성 처리하지 않는다.
- 중복 증거·다른 대상·잘못된 장소의 도착을 충족 수량에 더하지 않는다.
- 지연 도착은 수량 충족과 기한 미충족을 함께 보존한다.

모델 없이 실행하는 계약·업무 효과 테스트와 실제 모델의 자연어 해석 평가를 구분한다. 평가에는 문맥·기준 데이터·기대 의미·DB 효과와 변경되면 안 되는 사실을 포함하고 모델·프롬프트·사전 버전을 남긴다.

## 6. 기존 구현 비교에서 얻은 참고 사항

2026-10-06 대화에서 로컬 commit `2ea5997`을 기준으로 확인한 내용이다. 현재 배포 상태나 main의 상태를 뜻하지 않는다.

## 7. 설계 완성을 위한 논의 지도와 통합 제안

사용자의 요청에 따라 남은 논의 자리를 먼저 마련했다. 아래는 개발 백로그가 아니라 설계 질문 목록이다. 항목 등록이 기능 구현 승인이나 Phase 변경을 뜻하지 않는다. 구현은 범위를 확정한 뒤 이슈로 연결한다.

여기서 완성은 온톨로지·업무·Agent 계약을 대표 사례로 검증하고, 구현 범위와 남긴 한계를 설명할 수 있는 설계 기준선이 마련된 상태다. 이 완성 기준 자체도 제안이며 실제 구현·실환경 인수와 구별한다. 새로운 질문이 발견되면 항목을 추가한다. 이 목록이 도메인의 모든 질문을 이미 발견했다는 주장은 아니다.

### 진행 현황과 논의 묶음 (2026-10-06)

통합 제안 작성 전에는 26개 중 15개가 논의 중, 11개가 미논의였다. 통합 제안 작성 당시에는 D01~D26 모두 사용자 검토 대기였다. 2026-10-07 명시적 포괄 동의로 직접 코멘트 없는 23개 항목의 기본안을 채택했다. D02·D05·D14도 코멘트 없는 부분은 채택하며, 코멘트 범위의 보완안은 분리해 남긴다. 현재 결정의 적용 범위는 §10을 따른다. 설계 방향의 합의와 구현 명세·실환경 인수 완료는 구분한다. 항목 수는 중요도·소요 시간이 달라 완료율로 환산하지 않는다.

남은 논의를 다음 다섯 묶음으로 진행하는 안을 제안한다. 각 묶음이 정확히 한 번의 대화로 끝난다는 일정 약속은 아니다.

1. 개념·대상·수량·관계와 식별의 미정 부분: D01~D08.
2. 목표·책임·증거·예외와 업무 연결의 결정 정리: D09~D12.
3. 실제 구매·수입·보관·판매 흐름과 회수·정산 범위: D13~D19.
4. Agent·구축·외부 연동·저장·접근 통제: D20~D24.
5. 대표 사례 검증·인수 기준·운영·구현 순서: D25~D26.

이후 응답은 묶음별 설계안을 먼저 제시하고, 결과를 바꾸는 선택만 질문하는 방식으로 논의할 수 있다. 검토하지 않은 제안을 합의로 처리하거나 미논의 항목을 자동 확정하지 않는다.

### 7.1 사용 방법

- 상태는 `미논의`, `논의 중`, `제안 검토 대기`, `합의`, `범위 밖`으로 표시한다.

- 기존 합의는 §1을 따른다. 아래 `미정`은 남은 세부 결정을 뜻한다.

사용자의 명시적 포괄 동의를 현재 결정에 반영했다. D 번호를 유지해 코멘트 범위와 관련 보완안을 연결한다. 이미 동의한 기본안의 재승인을 요구하지 않으며, 남은 검토와 구현 시 구체화할 사항은 §10으로 구분한다.

##### 코멘트 반영 제안 v0.2 — 포장과 내용량 (2026-10-07)

단순히 같은 개별 포장 12개를 탈착 가능한 운송용 겉상자에 담았다면 같은 품목의 포장 단위·물류 단위로 표현할 수 있다. 반면 소비자가 구매하는 묶음 상품으로 규격·가격·표시·주문 조건이 구분된다면 별도 거래 품목과 포장 구성으로 연결한다. 12개가 함께 밀봉된 포장처럼 개별 포장 자체가 다르면 풀기만 해서 개별 포장 12개가 생기지 않는다.

품목별 포장 버전에 내용물 수량과 환산 기준을 둔다. EA를 사용할 때 무엇의 한 개인지 명시한다. 조회에서는 내용물 환산량과 포장별 재고를 함께 표시할 수 있으나 동일 물량의 단위 표현을 더해 중복 집계하지 않는다. 주문 이행은 요청된 포장 규격 또는 명시된 대체 허용 조건을 검사한다.

계산상 단위 환산과 실제 개봉·묶음·재포장은 구분한다. 실제 포장을 바꾸면 작업·수량·계보·판정 기록이 필요하며 자동 재고 전환하지 않는다. 재포장 작업의 운영 지원 여부는 범위 결정이 남아 있다. 명시적 대체 허용 없이 “같은 양이므로 이행 완료”로 처리하지 않는다.

수량은 수령·이동·출고·소비·조정 기록으로 대조한다. 파손은 우선 가용성 변경일 수 있으며 실제 수량 감소와 구별한다. 폐기·분실·샘플 반출은 각각의 활동으로 기록한다. 수량 차이를 허용할 경우 허용 오차와 승인 근거를 명시하고 원 차이를 남긴다. 독립 수요에 대한 배분 합계는 실제 물량을 초과하지 않게 한다. 물리적 분할은 원 수량 = 분할 결과 + 남은 물량 + 근거 있는 감소량으로 대조한다. 동일 거래 효과는 한 번만 반영한다.

##### 코멘트 반영 제안 v0.2 — 관측값과 파생 차이 (2026-10-07)

독립적으로 수정 가능한 차이 필드보다 지점·사건별 실제 관측값을 원천으로 저장하고 차이는 요청 시 계산하는 방향을 제안한다. 관측은 대상 물량·품목·포장·단위·구간의 출발/도착 지점·사건 시각· 기록 시각·출처·버전을 포함한다. 구간당 숫자 하나를 덮어쓰지 않는다. 관측인지 예정인지, 해당 물량 전체인지 일부인지, 누적량인지 현재량인지 명시한다. 실제 값이 없으면 0으로 간주하지 않는다.

단순한 동일 범위 운송에서는 출발 100상자, 도착 98상자로 부족 2상자를 계산한다. 두 값의 범위·측정 기준이 다르거나 미관측이면 비교를 보류한다. 분할되어 다른 지점에 2상자를 정상 인계했거나 나머지가 아직 운송 중이면 대조 범위·인계·이동 이력을 반영한다. 그 차이만으로 분실을 확정하지 않는다. 중량·수량은 같은 범위와 검증된 단위로 비교하고, 예정 대비 지연은 당시 유효한 예정 버전과 실제 사건 시각을 대조한다.

단순 재계산 결과를 별도 수동 입력 사실로 저장하지 않는다. 다만 차이가 알림·조사·승인의 근거가 됐다면 그때의 입력 참조·버전·계산 규칙· 결과를 판정 기록으로 보존한다. 정정 후 현재 diff와 당시 판단을 모두 설명할 수 있어야 한다. 파손 관찰·원인 조사·분실 확정은 파생 diff와 다른 사실·결정이며 별도 기록한다.

##### 측정 활동과 결과의 연결 (2026-10-07)

사용자는 “측정”도 동사가 될 수 있음을 제시했다. 측정하다를 활동 유형으로 두고 개별 측정 활동은 대상·측정 속성·방법·수행자 또는 장비· 장소·시점·결과를 연결하는 방향으로 반영한다. 수량 세기, 중량 재기, 온도 측정 등은 그 활동 유형의 구체적인 사용 예다.

측정값을 대상의 확정 속성으로 직접 덮어쓰지 않고 측정 결과에 값·단위· 적용 범위와 필요한 품질 정보를 기록한다. 현재 속성의 대표값으로 어떤 결과를 채택할지는 별도 규칙을 적용한다. 재측정은 새 활동과 결과로, 입력 오류 정정은 원 결과에 대한 정정 이력으로 구분한다.

목표를 부여한 측정 업무라면 완료 기준은 요청한 범위·방법·품질 조건을 충족하는 결과를 확보하는 것이다. 원하는 정상값이 나와야 완료되는 것은 아니다. 완료된 측정 활동과 유효한 측정 결과, 적합 판정은 서로 다른 설명이다. 장비 오류 등으로 유효 결과를 얻지 못하면 실행 시도 종료를 측정 목표 달성으로 해석하지 않는다.

관계 예: 물량 Q를 측정한 활동 M이 결과 R을 생성한다. 비교 활동 C는 출발·도착의 비교 가능한 결과 R1·R2를 참조해 차이를 계산한다. 측정, 비교·계산, 원인 조사, 허용·보류 판정은 구별한다. 단순 조회마다 영속 업무를 만들 필요는 없으며 판단 근거로 사용한 계산은 재현 가능한 입력·규칙·결과를 보존한다.

외부 문서의 수량이 모두 실제 측정 결과라는 뜻은 아니다. 예정값· 신고값·추정값·측정값과 그 출처를 구분하며 문서에서 읽었다는 이유로 Agent가 물리적 측정을 수행한 것으로 기록하지 않는다.

##### 비교 검토 — 독립 동사와 운송의 형용사형 설명 (2026-10-07)

사용자는 측정·비교·조사를 별도 동사로 관리하는 방식과 운송에 형용사형 속성·상태로 붙이는 방식의 적합성·구현 용이성 비교를 요청했다. 결론은 다음의 혼합안을 제안한다. 아직 채택된 구현 결정은 아니다.

1. 개념상 측정·비교·조사는 독립적으로 의미를 정의한다.
2. 실제 측정은 대상·방법·시점·출처·값을 가진 가벼운 활동 기록으로 둔다.
3. 운송에는 그 기록에서 유도한 측정 현황·수량 차이·조사 상태를 보여준다.
4. 담당·기한·대기·승인·후속 행동이 필요한 경우에만 별도 업무를 만든다.

활동의 식별과 목표를 가진 Work Item·Agent Run 생성을 동일시하지 않는다. 또한 하나의 동사마다 별도 테이블·서비스를 만들 필요는 없다. 측정 활동과 결과를 한 타입 있는 기록에 함께 보존할 수 있고, 반복 측정은 여러 기록으로 남긴다. 유형별로 필요한 입력과 제약은 명시한다.

| 비교 기준 | 운송의 단일 속성 중심 | 매 활동을 독립 업무로 관리 | 가벼운 활동 기록과 운송 요약 |
|---|---|---|---|
| 초기 구현 | 한 번의 값 저장·조회는 가장 단순 | 배정·전이·실행 연동까지 필요 | 기록 추가와 조회 변환이 필요 |
| 반복·재측정 | 이력을 추가하지 않으면 덮어쓰기 | 보존 가능하나 업무 수 증가 | 개별 기록으로 자연스럽게 보존 |
| 출처·정정·공유 | 배열·버전 등을 확장하면 구조가 복잡 | 업무와 증거를 모두 관리 | 원천 기록을 참조해 추적 |
| 책임·대기·재시도 | 별도 구조가 필요 | 적합 | 필요한 경우만 업무에 연결 |
| 운송 외 재사용 | 창고·반품마다 비슷한 속성이 증가 | 가능하지만 과도할 수 있음 | 동일 활동 구조를 다른 대상에 연결 |
| 조회 | 단순 | 여러 업무를 집계해야 함 | 파생 속성으로 단순하게 제공 |

“측정값 98상자”는 수량 속성이고 “측정 완료된 운송”은 파생 상태다. “측정하다”라는 활동의 시점·방법·출처를 두 표현만으로 보존할 수는 없다. 운송의 속성에 측정 배열과 모든 메타데이터를 넣으면 의미상 활동 기록을 내포한 구조가 된다. 표의 비교는 JSON 대 SQL이나 중첩 대 별도 테이블의 성능 우열을 주장하지 않는다. 물리적 저장 위치는 D23에서 결정한다.

구체적인 처리 제안은 다음과 같다.

- 정기 수량·온도 측정: 활동 기록을 추가하고 별도 Agent 실행은 만들지 않는다.
- 단순 diff 조회: 같은 범위의 유효한 측정값으로 계산한다. 영속 업무를 만들지 않는다.
- 부족·상충에 대한 재측정 요청: 담당·기한이 필요한 경우 업무를 만들고 그 업무에 여러 측정 시도와 결과를 연결한다.
- 원인 조사: 책임·증거 수집·외부 응답 대기가 필요하면 독립 업무로 둔다. 자동으로 끝나는 단순 확인은 계산·판정 기록만으로 처리할 수 있다.
- 운송 화면의 측정 완료·차이 있음·조사 중: 위 기록을 근거로 표시한다. 수동 편집 상태와 원천 기록을 둘 다 정답으로 두지 않는다.

예를 들어 출발 측정 M1=100상자, 도착 측정 M2=98상자를 보존하고 비교 가능한 범위의 부족량 2를 계산한다. 조사 업무 W를 만들었다면 운송은 W를 참조해 “조사 중”을 표시한다. 재측정 M3=99가 오더라도 M2를 삭제하거나 무조건 최신값으로 채택하지 않는다. 재측정과 정정, 유효 결과의 채택 기준에 따라 현재 요약과 과거 판단 근거를 구분한다.

근거 확인:

- [W3C SSN/SOSA 2017 Recommendation](https://www.w3.org/TR/vocab-ssn-2017/) 은 관측 활동, 관측 대상·속성, 절차, 시간과 결과를 구분한다.
- [W3C PROV-O](https://www.w3.org/TR/prov-o/)는 활동과 생성된 결과, 사용한 입력·주체의 출처 관계를 표현한다. 두 표준은 의미 분리의 참고이며 RDF 도입이나 모든 측정의 별도 업무 생성을 요구하는 근거가 아니다.
- 현재 commit `2ea5997`의 `AgentWorkService.create`는 자식 Work Item을 생성하면서 Run도 큐에 넣는다. 이 경로로 모든 측정을 표현하면 측정 사실 저장 외에 역할·실행 관리까지 연결된다.
- `RunCompletionPolicy`는 역할별 완료 근거를 검증하며 일반 측정 업무를 곧바로 지원하지 않는다. 범용 활동 구조가 이미 완성됐다고 볼 수 없다.
- 기존 `inbound_temperature_logs`와 `warehouse_temperature_logs`는 대상에 연결된 복수 측정값 기록을 사용한다. 새 수량·운송 모델에는 범위·단위·정정·품질 기준 등의 추가 설계가 필요하다.

- DDL과 backend 조사에서 별도 운송 건·구간 모델은 확인되지 않았다. `outbound`는 출고 기록이며 일부 코드의 `shipments` 변수도 이를 가리킨다. “기존 운송 객체에 속성만 추가”하면 끝나는 변경은 아니다.
- 온도 로그의 DDL은 있지만 해당 로그를 조회·기록하는 backend·CLI·MCP 업무 API는 조사 범위에서 발견되지 않았다. 새 기능에는 별도 API와 저장·연결 계약이 필요하다.

구현 난이도 비교는 코드·스키마를 읽고 필요한 구성 요소를 비교한 정성 판단이다. 구현 실험·성능 벤치마크·테스트 실행은 하지 않았다.

##### 채택한 보완 — C5 관측 이후의 대응 연결 (2026-10-07)

운송·창고 등에서 가벼운 관측 기록을 사용해도 대응 의무의 책임은 생략하지 않는다. 적용 정책상 대응 필요 여부를 판단할 담당·기준을 연결하고, 판단이 필요한 미확인 관측이 알림 뒤 사라지지 않게 한다. 유효한 대응 의무가 확인되면 D10의 담당 업무 연결과 D26의 실패 복구를 적용한다. 조달이 끝난 재고의 새 온도 이탈에도 같은 경로를 사용한다. 정상 관측이나 대응 의무가 없는 차이는 근거를 남기고 경량 기록으로 처리할 수 있다. 이는 관측마다 새 업무나 Agent 실행을 요구하지 않는다.

##### 채택한 보완 — C1 행동별 공급 적격성 (2026-10-07)

적격량은 행동·거래 문맥과 평가 시점을 명시한다. 판매를 위한 공급 가능량에는 D05의 해당 물량에 대한 처분 허용·제한을 적용한다. QC·규제· 고객 조건이 충족돼도 처분 근거가 미확인이면 확인된 공급 가능량에 넣지 않으며, 물리 보유량과 미확인 범위는 별도로 보존한다. 판매 불가가 반송 등 다른 행동까지 일괄 금지한다는 뜻은 아니며 행동별 근거로 판단한다.

다른 조건이 같고 두 범위가 구별되는 위탁판매 허용40과 고객 보관 전용60은 보유량100, 판매 적격량40으로 조회한다. 활성 예약이 없을 때 미예약 판매 적격량도40이다. 앱 권한 변경이나 QC 해제만으로 나머지60을 더하지 않는다. 이미 예약된 물량의 처분 허용이 만료·취소되면 부적격 예약의 책임을 유지하고 D17의 대체 할당·담당자 판단 경로를 적용한다.

##### 통합 제안 v0.1

운영 화면과 대화에서 미달 목표·다음 행동·담당·대기 조건·기한· 증거 충돌을 조회하게 한다. 책임 없는 업무, 확인 시점이 지난 대기, 누락 이벤트·재고 불일치를 탐지해 정해진 담당자에게 전달한다. 같은 문제의 반복 알림을 묶고 자동 승인이나 자동 성공으로 처리하지 않는다.

장애 복구는 마지막으로 확정된 기록과 요청 식별자로 재개한다. 외부 쓰기 결과가 불명확하면 대조 후 재시도하고 무조건 반복하지 않는다. 구현 순서는 대표 fixture와 읽기 → 한 건의 구매·도착 목표 → 부분 수령·QC·판매 → 외부 연동·회수의 순서를 제안한다. 논리적 의존 순서이며 실제 착수는 기존 보드·Phase·이슈와 대응해 결정한다. 운영 전 인증, 필수 통제, 백업·복구와 실제 모델 인수는 별도 통과 기준으로 둔다.

- 이전 검토 기록: 미정. 위 내용은 아직 승인된 결정이 아니다.

##### 채택한 보완 — C5 접수부터 업무 연결까지 복구 (2026-10-07)

활성 부모가 없는 관측도 접수·대응 필요 판정·담당 업무 연결의 진행을 추적한다. 대응 의무가 확인됐으나 생성·배정·연결이 실패한 경우 미해결로 남기고 접수 책임자와 다음 확인 시점을 유지한다. 복구는 이미 연결된 업무와 원천 요청을 대조해 같은 의무를 중복 생성하지 않는다.

담당 업무 연결 또는 추가 의무 없음의 근거 있는 판단이 확인돼야 접수 추적을 끝낼 수 있다. 알림 전송 성공은 책임 연결 완료의 증거가 아니다. 실제 업무 책임은 D10의 초기 배정·인계 규칙을 따르고, 연결된 업무가 끝나기 전에 접수 추적을 끝내더라도 그 업무의 책임은 유지한다.

## 9. Adversarial debate 검증 (2026-10-07)

사용자 요청으로 gpt-6-astra xhigh agent 4개가 동결본을 독립 검토하고 상호 반론하는 2라운드를 수행했다. 자세한 공격·방어·철회와 코드 근거는 [검증 보고서](reviews/2026-10-07-ontology-adversarial-debate.md)에 남겼다.

혼합안은 유지할 수 있다는 검토 결과다. 명시적인 자기모순은 찾지 못했으나 설계·구현의 완전성을 증명한 것은 아니다. 핵심 보완 제안은 다음 두 가지다. 검증 보고 당시에는 제안이었으며, 이후 사용자의 포괄 동의를 §10에서 반영했다.

- D03·D16·D18: 통합 후 계보상 출처와 현재 실물 식별 가능성을 구별한다. A40+B60이 구별되지 않는100으로 합쳐지면 A의 영향 후보가 현재100에 걸칠 수 있다. 임의의40만 제외하고60을 정상으로 간주하지 않는다. 후보 범위와 오염 확정·보류 결정은 구분한다.
- D11·D12·D26: 종료 후 정정으로 유효한 미이행 의무가 확인되면 기존 업무 또는 인수된 후속 업무에 책임을 연결한다. 통지만 하려면 추가 의무가 없거나 책임 연결이 확인됐다는 근거가 필요하다.

실제 재고 쓰기 전에는 관측 채택과 수령 정정·조정을 분리하고, 예약 대체 시에는 현재 효력과 이력을 구별한다. 외부 연동과 버전별 실행은 원천 namespace·revision, 지원 정의 버전·처리기 대응을 정한다. 이는 기능별 구현 전 계약이며 혼합안 자체의 반증은 아니다.

10개 초기 주장 중 물량 식별과 종료 후 책임은 좁혀 유지했다. 기대 측정 범위·인계·관측 이상은 기존 규칙에 통합하고, 포장 불일치 정산의 원 반례는 기존 품목·항목 구분을 어겨 철회됐다. 원 D01–D26의 제안과 코멘트는 보존했다. 구현 코드·테스트·보드는 변경하지 않았으며 실행 테스트·벤치마크·실환경 인수는 수행하지 않았다.

| C1–C5 | D25 | 사례별 입력·기대 업무 결과와 관련 규칙의 대응 |

이번 설계 문서 보완은 완료했다. §10의 기존 합의와 다른 코멘트 범위는 유지하며, 이번 지시를 그 밖의 보완안 전체나 코드·DB 구현의 승인으로 확대하지 않는다. D25 사례는 실행 인수 결과가 아니라 구현 시 검증할 명세다. 검토 보고서는 당시 판정·해시·행 번호를 유지한다.

## 13. 팀 설명 초안 (2026-10-07)

사용자가 최초 기획과 현재 설계의 차이를 팀원에게 설명할 필요를 제기했다. [팀 공유 초안](ontology-design-philosophy.md#transition)에 최초 제조·현지화 기획, fork에 이미 기록된 변경, 이번 완제품 수입·유통 설계를 구분했다. 변경 이유·기존 작업의 재사용·추가 전환 비용·팀과 정할 범위를 정리했다. 공동 프로젝트의 방향이 바뀌었다고 확정하거나 실제 메시지를 보내지는 않았다.

후속 요청으로 팀 공유 초안을 도식 3개 중심으로 재구성했다. 제조와 수입·유통의 범위 비교, 100상자 목표의 부분 수령·잔여 책임, 기존 기반과 새 설계의 구현·검증 연결을 순서대로 설명한다. 각 그림 아래에 의미와 적용 범위를 붙이고 팀의 결정 사항도 세 그림에 대응시켰다.

## 14. 기획안 전체의 도식 설명 (2026-10-07)

사용자가 기획안의 모든 부분을 도식으로 차례로 설명해 달라고 요청했다. [전체 도식 설명서](ontology-design-philosophy.md#workflows)에 D01–D26을 12개 도식으로 묶고 범위·대상·권한·사건·목표·책임·실제 업무·Agent·저장·검증의 순서로 설명했다. 항목 대응표와 수량 사례를 포함하고 아직 별도 제안인 포장·계약 관리·관측 방식의 세부 내용은 구분했다. 새 설계 결정을 추가하거나 구현 완료로 바꾸지 않는다.

## 15. 통사론 기반 설계 설명의 누락 보완 (2026-10-07)

사용자가 “통사론 기반 설계에 관한 내용은 어디 갔는가”라고 지적했다. 기존 §1.2·§2·§4에는 내용이 남아 있었지만 전체 설명에서 설계의 중심 원리로 제시하지 못했다. 업무 범위와 흐름 위주 설명의 누락을 인정한다.

§1.6과 전체 도식 설명서 0번, 팀 공유 초안 0번에 명사·형용사·동사의 개념적 역할과 허용된 결합 구조를 복원했다. 동사형 관계·활동·목표 업무, 대상·업무의 두 진입점, FDE 구성과 운영 Agent의 한계도 함께 연결했다. 전체 설명서는 공통 원리 1개와 업무 적용 12개, 총13개 도식이 됐다. 문장 구조·업무 의미·사실 증거·실행 권한을 구분하며 기존 합의를 넘어 새 문법 엔진이나 자동 코드 생성을 확정하지 않는다.

## 16. 통사 규칙에서 예시 워크플로우로 설명 재구성 (2026-10-07)

사용자가 설명 문서를 통사 규칙 기반에서 시작해 예시 워크플로우를 설명하는 방향으로 개선하고 도식을 활용하라고 요청했다. [전체 설명서](ontology-design-philosophy.md#workflows)의 본문을 주제별 나열에서 어휘·결합 규칙 → 사실·조회·목표 요청 → 의미·증거·권한 검증 → 하나의 연속 업무 사례 순서로 재구성했다.

비스킷100상자의 발주와60+40 분할 수령,40의 QC 보류,60의 예약·출고· 고객 인도,20의 실제 반품을 도식과 수량표로 연결한다. 누적 조달 도착· 현재 보유·판매 적격·예약량을 구별하고, 과거 인도 기록의 정정은 별도 분기로 설명한다. 업무 종료 뒤 관측의 책임 연결과 D01–D26 대응표도 유지했다. 팀 공유 초안의 설명서 안내를 새 구성에 맞췄다.

이는 설명 순서와 예시의 개선이다. §10·§12의 채택 범위와 별도 보완 제안의 상태를 유지하며 API·DB·DSL·실행 정책을 새로 확정하지 않는다.

문서 대조 검토에서 B40의 기존 QC 후속 책임과 부모 없는 새 이상 사례가 섞이지 않도록 §9를 보완했다. 설명서의 Mermaid 도식12개에 대한 구조 점검, 로컬 링크·Markdown fence 확인, D01–D26 대응과 연속 수량표의 계산 대조를 마쳤다. Mermaid 렌더링과 코드·업무 실행 테스트는 하지 않았다.

## 17. 통사구조와 두 관리 진입점의 설계 철학 (2026-10-07)

사용자가 업무 절차보다 통사구조를 이용한 설계 철학에 중심을 옮겨, 명사·동사에서 시작하는 관리와 양쪽에 형용사를 붙여 속성을 더하는 철학을 도식과 글로 설명하라고 요청했다.

[설계 철학 설명](ontology-design-philosophy.md)에 두 관리 진입점, 형용사형 설명의 점진적 구체화, 같은 대상·업무·증거를 공유하는 연결을 도식4개와 사례로 작성했다. 대상의 현재 상태와 업무의 목표 조건, 업무 유형과 개별 업무, 속성·관계·증거 기반 판정의 차이를 유지했다. 기존 워크플로우 설명서에서는 이 문서를 설계 철학의 선행 읽기로 연결한다. 새로운 구현 결정이나 기존 보완 제안의 일괄 채택을 추가하지 않는다.

설명 대조 검토에서 첫 도식의 업무 유형과 개별 업무를 분리해, “대기 중인” 설명이 유형이 아닌 O1에 붙도록 보완했다. 도식4개의 소스 구조와 문서 링크를 확인했으며 렌더링은 미확인이다.

## 18. 설계 철학을 기준으로 설명 문서 통합 (2026-10-07)

사용자가 다른 설명 문서를 설계 철학 기준으로 합치고 예시 워크플로우도 그 철학으로 설명하라고 요청했다. `ontology-design-philosophy.md`를 현재 설명의 기준 문서로 삼고 `ontology-visual-guide.md`의 업무·운영· 검증 내용과 `ontology-transition-brief.md`의 기존 기획·fork 비교를 통합했다. 두 이전 파일은 중복 본문 대신 통합 문서 안내로 남긴다.

통합본은 철학1–6장, 적용 사례7–12장, 해석·구현·검증13장, 기존 기획과의 연결14장, 채택 범위와 근거15장으로 구성한다. 각 사례는 명사·동사의 진입점, 양쪽에 더하는 설명, 활동 증거와 판정, 남은 책임을 연결한다. 연속 수량표와 D01–D26 대응, 세부 보완안의 제안 상태, 과거 fork commit의 근거를 보존한다. 과거 원격 상태를 현재 확인한 사실로 이월하지 않는다.

논의 기록과 두 검토 보고서는 합의·반례·판정의 이력으로 유지한다. 이 통합은 새 설계 결정, 공동 프로젝트의 범위 변경 합의, 코드·DB 변경, 원격 게시나 메시지 전송을 포함하지 않는다.

통합 전후 문서 대조 검토에서 중대한 누락이나 수량·의미 모순은 발견하지 못했다. 통합본15개 장·도식11개의 소스 구조, D01–D26 대응, 수량표6행, 로컬 링크와 절 이동 링크를 확인했다. 렌더링과 업무 실행 검증은 수행하지 않았다.

## 19. 통합 후 기존 설명서 삭제 (2026-10-07)

사용자 요청으로 안내 파일로 남겼던 `ontology-visual-guide.md`와 `ontology-transition-brief.md`를 삭제했다. 이 기록의 기존 링크는 통합 설명서의 해당 절로 연결했다. 현재 설명은 통합본에서 관리하며 논의·검토 이력은 유지한다.


## 20. fork 재작성 방향과 기술 스택 논의 (2026-10-07)

사용자는 fork main의 기존 구현·관련 문서를 대체하고 새 온톨로지 설계를 구현하는 계획을 시작하되 먼저 기술 스택을 정하자고 했다. SAP internship을 목표 중 하나로 유지하며 제품 적합성을 우선한다. 추가 질문에는 목표 직무를 BTP·클라우드·백엔드 개발로 명시했다.

[별도 구현 계획](ontology-implementation-plan.md)에 CAP Java+PostgreSQL 우선 검증 제안, Spring Boot+jOOQ 대안, CDS와 FDE 정의 데이터의 경계, SAP 공식 문서의 PostgreSQL·버전·인증 제한, 최소 검증 조건을 기록했다. 기존 구현의 재사용은 새 계획의 필수 전제가 아니다. 스택 추천은 아직 사용자 합의가 아니며 코드·DB·원격 브랜치 변경이나 실제 검증을 수행하지 않았다.

fork main·기본 브랜치·통합 브랜치의 SHA는 현재 조회했다. 보드 project items는 조회 실패했으며 milestone·issue는 REST에서 확인했다. 계획의 Git 전환·삭제 범위·복구·새 개발 목표 대응은 후속 논의로 남긴다.

## 21. 구현 문서 분리와 사용자 선택·Sol high 검토 (2026-10-07)

사용자는 Java25 제안을 Java21로 바꾸고 최신 stateless MCP와 Agent Skills를 구축 범위에 포함하라고 했다. 네 가지 스택 인수 영역은 GPT-6.1 Sol high adversarial debate로 검토하며, 구현 관련 내용은 통합 설명서 밖에 기록하도록 했다.

기술 스택과 구현·전환·실행 검증 자료는 [구현 계획](ontology-implementation-plan.md)으로 옮겼다. 통합 설명서에는 철학·업무 사례·채택 범위와 구현 문서 연결을 남겼다. Java21·MCP2026-07-28 stateless·Agent Skills는 사용자 선택이며 CAP·PostgreSQL·BTP의 구체 조합은 검증 후 채택할 후보다. Skill 파일과 MCP adapter가 구현됐다는 뜻은 아니다.

실제 GPT-6.1 Sol high 검토자 세 명의 독립 공격·교차 반박을 수행하고 [검토 보고서](reviews/2026-10-07-ontology-stack-sol-high-debate.md)를 작성했다. 기존 설계의 개념 모순보다 인수 조건의 공백이 확인돼 V1–V8에 의미 버전·물량 경합·제한과 출고·우회 쓰기·기한 복구·멱등성·비동기 권한·플랫폼 실증 계약을 반영했다. 논리 검토 완료와 실제 런타임·DB·인증·배포 인수를 구별하며 후자는 미실행이다.


## 22. 구현 계획 완결성의 반복 검토와 보완 (2026-10-07)

사용자가 GPT-6.1 Sol high adversarial review를 반복하고 온톨로지 설계를 구현하기에 충분히 완결될 때까지 구현 계획을 수정하라고 요청했다. 스택 검토만으로 완료하지 않고 D01–D26 전체를 대상으로 검토했다.

[구현 계획](ontology-implementation-plan.md)에 모듈·데이터/통사 계약·도메인 command·업무/의무 상태·승인/권한·멱등성·FDE·MCP/Skills·복구·S0–S6 통합 gate·R1–R9 결정 register·D/T/C/V/E 인수 추적표를 작성했다. 미채택 D02/D05/D14 상세 보완안을 일괄 승인한 것으로 처리하지 않았으며 사용자 선택 Java21·stateless MCP·Agent Skills와 fork 재작성 방향을 유지했다.

독립된 실제 GPT-6.1 Sol high 검토자 세 명의 세 차례 검토와 최종 교정 확인에서 실행 명령과 사실 관측의 혼동, 일반 이동을 통한 출고 우회, 허위 FULFILLED 종료, 의무 이전의 책임 단절, 무이벤트 만료 대응, 관리 명령 누락, Step 인수의 순환 의존을 발견·수정했다. 최종 권한표의 잔존 충돌까지 현재 파일을 다시 읽어 확인한 뒤 각 담당 범위에서 계획 완결성 PASS를 받았다. [검토 보고서](reviews/2026-10-07-ontology-implementation-completeness-sol-high.md)에 기준선 hash·반례별 처분·요구 감사와 미실행 범위를 남겼다.

완료한 것은 구현 계획의 문서 계약과 논리 검토다. 실제 code·DB·MCP/Skills 구축·법규·실모델·BTP 인수는 미실행이며 계획에 해당 gate를 명시했다. 원격 이슈/보드·PR·브랜치·배포 상태는 바꾸지 않았다.
